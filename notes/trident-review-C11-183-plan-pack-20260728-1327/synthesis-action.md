## Surface to user (do not apply silently)

- **S1: Eight of nine reviewers recommend inverting the Bonsplit relationship: pure shape in the package, clock and policy in c11**
  - Why deferred: design-needed / author-intent-needed. The direction is near-unanimous, but executing it restructures Phases 1 and 2 and changes what is offered upstream. That is the plan author's and operator's call, not a synthesis edit. I1 requires the decision be recorded; this is the substance of the recommendation.
  - Summary: The concrete counterproposal is to promote `TabActivityMark` / `TabActivityMarkMetrics` out of `Internal/` into a public, dependency-free mark view that takes its animation phase as plain inputs (`fillCount: Int` defaulting to full, `coreOpacity: Double` defaulting to 1.0, `side`, `color`), following the existing `flashGeneration: Int` precedent already carried on Bonsplit's `TabItemView`. c11 then imports and renders the same view in the sidebar (`ContentView.swift` already `import Bonsplit`), and owns the single clock in `Sources/` where app-active and accessibility state already live. Claimed consequences: geometry drift becomes structurally impossible rather than mitigated by "review the final diff side by side" (which is the plan's weakest mitigation and the only proposed answer to the ticket's "Both renderers draw the new set and agree" acceptance criterion); Phase 2's second submodule cycle disappears entirely, dissolving B2; the upstream offer becomes shape-plus-optional-input, a strictly easier sell than a public timer API whose only in-package consumer is one 9pt mark; and post-gate timing tweaks become one-repo edits instead of submodule round trips. The counter-case the plan could make, and does not: if the sidebar's geometry needs genuinely diverge from the tab chip's (the 10pt summary scale in I2 is the live example), sharing a view across the module boundary gets awkward. The plan does not argue either side, which is the gap.
  - Sources: standard-claude (architectural assessment, alternatives, Q5/Q6), standard-codex (clock ownership, "host-owned injected shared clock", Q2), adversarial-claude (D1, Q7, uncomfortable truth 4), adversarial-codex (challenged decisions, Q3/Q16), adversarial-gemini (challenged decisions, uncomfortable truths, Q1/Q3), evolutionary-claude ("the inversion", suggestions 3-4, Q1/Q2), evolutionary-codex (section 1, Q2/Q3/Q12), evolutionary-gemini ("abstract the metronome"), standard-gemini (Q1, milder form).

- **S3: Whether the flag-tier visuals should ship in C11-183 at all, and how the Bonsplit-side modifier seam is actually reachable**
  - Why deferred: scope-creep / design-needed. Two distinct proposals point opposite ways and both touch the plan's central forward-compatibility bet.
  - Summary: The plan ships the violet recolor, the 0.4s flagged-waiting flash, and flag-over-suppression while the non-goals forbid every primitive that could set `flagged` or `suppressed`. Reviewers note two consequences. First, this is several hundred lines of visual behavior that no human or agent can trigger, handed to a validation stage with no way to see it: the first human to see the alarm flash sees it in production. ## Evolutionary worth considering (do not apply silently)

- **E1: Name and build the clock as a general c11 primitive, not a mark-specific one**
  - Summary: The eligibility model being built here (app-active, workspace-selected, pane-collapsed, viewport-intersecting) is the genuinely hard and reusable part, and c11 has no shared animation clock today. Naming it generically (`C11AnimationClock` / `WorkspaceMetronome`) with token-based registration would let `SidebarDecayClock`, the hand-rolled tab `flashGeneration` one-shot, and staleness polling migrate onto it over time, instead of each spawning its own timer.
  - Why worth a look: It is a naming and placement decision made once, at near-zero extra cost now and real cost to retrofit later, and it compounds with S1's clock-ownership question rather than competing with it.
  - Sources: evolutionary-claude ("the clock as a general c11 primitive", suggestion 4), evolutionary-gemini ("abstract the metronome"), evolutionary-codex (mutation 3).

- **E2: Keep `fillCount` an input so the working fill can later be driven by real throughput**
  - Summary: The typewriter fill is currently decorative: nine dots on a fixed 4s cycle regardless of what the agent is doing, so a hung agent stuck in `working` ticks merrily forever, implying liveness the mark does not measure. c11 already sees PTY output volume. Deriving fill from actual output throughput is explicitly wrong for this ticket (it breaks the shared-clock coalescing model and probably the latency budget), but keeping `fillCount` an input to the mark rather than deriving it internally from phase preserves the option for free.
  - Why worth a look: It is a one-line API-shape choice now that keeps a genuinely valuable future capability reachable, and it is one more argument for the pure-function mark in S1.
  - Sources: evolutionary-claude (blind spot B3 in adversarial-claude, mutation "typing as the fill source"), evolutionary-gemini ("throughput-coupled motion", Q4), adversarial-claude (B3).

- **E3: Injectable phase source in DEBUG for deterministic visual review**
  - Summary: Making the phase source injectable under `#if DEBUG` would let a reviewer freeze every mark at phase 0, mid-fill, full-hold, dip-minimum, and flash-white, turning shape and motion review into reproducible screenshots rather than wall-clock timing luck. Distinct from a QA harness: it is a seam on the clock, not a rig.
  - Why worth a look: It makes the visual validation the operator does want cheap and repeatable, and it is the same seam that would make any future motion tuning checkable; it overlaps with the contact-sheet proposal in S3, so consider them together.
  - Sources: evolutionary-codex (mutation 1), evolutionary-claude ("the marks contact sheet").
