# c11 relay: build-host agents talk back

Plan ticket 14 (C11H-16), Settled 9 and 17. An agent in a c11 terminal on another machine runs `c11` the way a local agent does: it names its panel, sets its description and status, raises a flag, sends mail and reads its own mail. Calls reach c11 through hc's existing machine link while the operator's Mac is awake. Any relayed command may wait through a short reconnect for its initial read probe. A write follows only after the probe answers, at most once. Telemetry that still cannot be claimed waits in a small spool until the link returns.

**Only a c11 terminal's own calls are served, and only as its own panel** (C11H-176, relay protocol 2). Each terminal c11 opens on another machine gets its own credential, and every call it makes is signed with it. A process on that machine that is not running in a c11 terminal is refused: a plain ssh shell, a cron job, another app's terminal, or a script that copies `C11_PANEL_ID` and `HC_TERMINAL_ID`. So is a c11 terminal that claims another panel, a copy of an earlier call, and a terminal left on a machine that was removed and added again. What it does not stop is in "What authentication does not cover" below. c11 logs the boundary at every link-up (`hc.relay up ... trust=per_terminal_credential`).

## How a call travels

hc keeps a small document store per core and reports each change as a `doc` event, including to a core linked to it. The relay uses that and nothing else: no daemon runs on the build host, no second ssh opens, and nothing is written to the build host's shell files or other tools' configuration.

1. `c11` in a build-host terminal is c11's relay shim (`~/.local/share/c11/relay/<session>/bin/c11`). It runs the c11 CLI in relay mode, which talks only to the build host's own c11 hc core socket.
2. The CLI takes a free request slot (`c11h.relay.r00` .. `r31`) by compare-and-set and writes the socket request line (v2 JSON or v1 text, unchanged) with its identity: `C11_PANEL_ID`, `C11_WORKSPACE_ID` and `HC_TERMINAL_ID`.
3. c11 on the laptop gets the doc event over its hc connection, reads the slot, checks the caller and the method, and claims the slot by compare-and-set.

   If c11's terminal inventory is refreshing at that moment (a panel close or creation does this for a few tens of ms), c11 claims the slot anyway. It then checks the caller once the inventory is ready, waiting at most 2 s or half the call's reply budget. It refuses with `relay_inventory_pending` only if the inventory is still not ready by then. A refresh also reopens hc's event stream, so when the subscription is renewed, or hc reports `missed` events, c11 reads every request slot once and claims any request whose event it never got.
4. It runs the request through the same socket command processor a local caller uses, off the main thread, with the verified panel as the caller, and writes the reply into the slot. The CLI reads it and frees the slot.

**Bounded reconnect wait.** Any relayed command, including a write, may wait up to about 10 s while the link reconnects because its first call can be a read probe such as `system.capabilities`. Read-only calls and spoolable telemetry allow up to 10 s for a claim, capped by the caller's timeout (including shorter hook deadlines); claim and reply share that timeout. After the probe answers, other writes are sent at most once, with their own 1.5 s claim bound (`C11_RELAY_CLAIM_MS`, 250 to 2500), and are never queued or replayed. The short claim bound is per write, not the whole command's elapsed time. At expiry the CLI cancels by compare-and-set: either the cancel or c11's claim wins, never both. A missing reply after a claim is an uncertain outcome. After one unclaimed call exhausts its bound, the shared latch makes the rest of that CLI command fail immediately, including any pending write. A flapping link can cost the tolerance per read until a claim times out. Local hc document operations have their own 1 s I/O bounds; a stalled local core can add that overhead. Nothing waits on c11's main thread.

**Is the link up?** c11 writes a small heartbeat, `c11h.relay.seen`, on each linked machine at link-up and every 2 s. It carries when c11's machine-link monitor last saw that link go down and come back. When a claim times out, the CLI reads it and the error says which case it is:
- **The link dropped and came back** in the last 2 minutes: `relay_unreachable: the machine link to c11 dropped N s ago and has been back for M s; nothing ran. Retry.`
- **c11 answered in the last 8 s:** `... it answered over the machine link N s ago, so the link is up; nothing ran. Retry.`
- **c11 has gone quiet:** `relay_unreachable: no answer from c11 over the machine link for N s; the link is probably down and reconnects on its own (or the Mac running c11 is asleep); nothing ran. Retry shortly.`
- **No heartbeat at all:** the "is the Mac running c11 awake?" text, noting that c11 has not answered over this link yet.

c11 logs event-to-claim latency as `hc.relay claim-latency n= p50= p95= max= rescans=` every 50 claims or 60 s, and any claim over 500 ms on its own line (`hc.relay slow-claim`).

**Spool.** Only telemetry spools: `set-status`, `clear-status`, `set-progress`, `clear-progress`, `log`, `clear-log` and `agent-event append`. When its claim times out, the CLI adds the request to `c11h.relay.spool` (at most 256 records, 256 KiB) and exits nonzero saying it was spooled. A full spool says so and drops the record. c11 drains the spool when the machine connects, when the event subscription is renewed, when hc reports `missed` events and when the spool changes. It drains only against a ready terminal inventory: while the inventory is pending the spool stays untouched and drains once it is ready. It claims every record at once, then applies them in order, before any later request from that machine. Nothing is applied twice; a crash between the claim and the apply loses those records.

## What the relay carries

Default deny. Allowed: identify, ping, capabilities, tree and list reads and panel and workspace metadata (title, description, agent, custom keys; each inside the caller's workspace, below), rename, sidebar status, progress and log, flags (raise and lower), notifications, journal appends (an `interactive_pid` in one is dropped: it names a process on the other machine), fleet reports (`agent.report`: the calling panel's login name, final message and failed turn, bounded by its parser, never spooled), `mailbox.resolve`, and the relay mail methods. Everything else is refused with `relay_not_allowed`: `send`, `send-key`, `paste`, creating or closing panels, areas and workspaces, `launch-agent`, browser and markdown commands, `rpc` of any other method, hooks.

**Writes name only the caller's own panel and its workspace** (C11H-176). A relayed rename, metadata write, flag, flash, notification, fleet report or sidebar status, progress and log acts only on the calling panel and the workspace that holds it now, as c11's own model places the panel. A panel target must be the caller's UUID: another panel, a short ref such as `panel:3`, or another kind of target (window, area, a source or destination) is refused with `relay_target_refused`. The workspace is always replaced with the panel's own, so a panel that moved keeps working with its launch-time `C11_WORKSPACE_ID`. A v1 sidebar line is rebuilt from the tokens its handler reads: every target option the caller wrote (`--tab`, `--workspace`, `--panel`, `--surface`, `--pane`, `--area`, `--window`, `--pid`, however quoted) is dropped and c11's own `--tab=<workspace> --panel=<panel>` lead, so no handler falls back to the selected workspace or the focused panel. Notifications go only through `notification.create_for_panel`, without the calling machine's `agent_pid` or Codex payload. A relayed flag is always the agent's (`by` is `agent`). A panel may not set its `mailbox.address` or `mailbox.role` to a value another live panel answers to as its address, role or title (`relay_identity_taken`).

**Reads see only the caller's workspace** (C11H-371): the workspace that holds the calling panel now, as c11's own model places it. A relayed read that names another workspace, a panel or area outside the caller's workspace, a window that does not hold it, or a target that resolves to nothing, answers `not_found` and does not run; every spelling of a target counts (`panel_id`, `surface_id`, `tab_id`, refs such as `panel:3`, `area_id`, `window_id` and the rest). The workspace the request claims (its launch-time `C11_WORKSPACE_ID`) names the caller's own, so a moved panel keeps reading its workspace. A read with no target reads the caller's panel or workspace, never the operator's selected workspace or focused panel. `tree` with `--all` or `--window` is the caller's workspace, `identify` reports the verified caller and the operator's focus only when it lies in that workspace, `list-windows` and `current-window` name only the window that holds it (and none of its other workspaces), `list-workspaces` and `current-workspace` only that workspace, and `family` keeps that workspace's panels plus the caller's own parent, wherever it is, with just its id, workspace and state (for `mailbox send --to-parent`). v1 `list_status` and `list_log` are rebuilt like a sidebar write, led by `--tab=<the caller's workspace>`. Mail routing still reaches every workspace: `mailbox.resolve` answers for any recipient, but carries no other panel's session id or shared-inbox members. `display.list` lists the displays and only the window that holds the caller's workspace. `get-metadata` names a parent or delegator only when it lies in that workspace, and a tree's Captain fields name a holder only inside it (the Captain's address and whether one is present stay). Ping, capabilities, brand and the flag-kind registry carry no panel and pass as asked. Local reads are unchanged.

**Identity.** The request's `C11_PANEL_ID` must name a running c11 panel whose terminal is on the machine the request came from, and that terminal's id must equal the request's `HC_TERMINAL_ID`; otherwise `relay_identity_refused`. Both are public on that machine (`hc ls` shows them), so this only finds the terminal; the credential below proves the caller is it. The verified panel becomes the caller for flag attribution, the mail sender and `caller_panel_id`; caller fields in the request are replaced by it. A journal event (`agent-event append`) must name that same panel in `tab_id` / `panel_id`, or it is refused.

## Authentication

**The credential.** c11 on the Mac keeps one random 32-byte secret per hc session and linked machine, in `~/Library/Application Support/c11/relay/keys/<session>/<machine>.json` (a 0600 file in 0700 folders, never read through a symlink, never sent anywhere). A tagged build's session has its own. Each terminal's credential is an HMAC of that secret over the session, the machine, the panel and the terminal's creation id (its `c11.creation` label). It is derived when needed and never stored, and a terminal opened again for the same panel gets a new one.

**How a terminal gets it.** hc saves a terminal's launch environment in plain text on that machine (`restart_env` in `terminals.json`), so the credential never goes there. Before `terminal.run`, c11 writes a pickup document, `c11h.relay.k.<first 16 hex digits of the creation id>` (hc allows 32 characters), holding the credential masked by a random pad, and puts only the pad in the launch environment (`C11_RELAY_PICKUP`). The terminal's launch line runs the relay `c11 relay-pickup` once, before the login shell, whatever that shell is: it reads the document, deletes it by compare-and-set, unsets the pickup variable and exports `C11_RELAY_AUTH`. The pad alone and the document alone reveal nothing, and the document exists only while the shell starts; c11 deletes one nobody claimed after 60 s. A pickup that fails (no document, a conflict, a core that does not answer within its short bound) prints nothing, and the shell starts as usual without a credential. The variable's name leaves out KEY, SECRET and TOKEN, because Codex drops variables whose names contain them from its tools' environment.

**Each call.** The CLI reads a nonce from c11's heartbeat (`c11h.relay.seen` carries a fresh one every 2 s) and signs the request with its credential: an HMAC over every field, length-prefixed, including the line, the panel, the terminal, the timeout, the nonce and whether it is signed for a slot or for the spool. c11 checks, in order: protocol 2 (an older kit's request is refused with `relay_kit_outdated`); the identity above; that the terminal has a credential (`relay_auth_missing`); that it was made for this terminal's current creation under the current secret, that the HMAC matches, that it was signed for a slot, that its pickup was not left unclaimed, and that c11's own records (the creation intents it keeps for each panel, not hc's labels) still make that creation the panel's current terminal on this machine (`relay_auth_refused`); that the nonce was issued to this machine in the last 64 s (`relay_stale`, which the CLI retries once with a fresh nonce, since nothing ran); and that the request id is new (`relay_replay`). Then the method policy below. A `done` reply carries c11's HMAC under the same credential; the CLI refuses a reply that does not verify (`relay_reply_unverified`) and does not use what it says. A refusal c11 makes after authenticating the caller is signed too. Before that (identity, credential, an older kit) it cannot be, so for an unsigned refusal the CLI shows its own text for that code, never the slot's, and after c11 claimed the call it reports an unsigned refusal as `relay_outcome_unknown`.

**Spooled telemetry** is signed for the spool only, so a spooled record never runs from a slot and a live request copied into the spool never runs from it. c11 drops a record more than 24 h old and one whose id it already applied for that terminal; the applied ids are kept on disk per terminal for a day and an hour (`relay/spool-applied/<session>.json`) and written before the records run, so a copy is refused across restarts too and a crash mid-drain loses telemetry rather than repeating it.

**Seen from the Mac.** The first time a terminal's calls are refused for its credential or an outdated kit, c11 writes one line naming the machine, the panel and the code to `~/Library/Logs/c11/hc-diagnostics.log` (`event=relay_refused`) and to the relay log (`hc.relay auth-refused`). The CLI on that machine prints the refusal with what to do.

**Removing a machine** (Settings > Herder Topography > gear > Remove, or `c11 machine unlink`) deletes its secret in this app's own sessions. Every credential made from it stops verifying, including a terminal left running there because the link was down, and a terminal that survives until the machine is added again. Adding the machine again makes a new secret. Removing a machine with a hand-run `hc machine rm` does not revoke anything, and linking an existing name again does not rotate the secret; remove it through c11 first.

**A pickup nobody claimed.** c11 records each pickup it writes (`relay/pickups/<session>.json`). Sixty seconds later, or at the machine's next link-up if c11 quit in between, it looks again: its own document still there was never claimed, so c11 deletes it and, only if that delete wins, refuses that creation's credential from then on, whoever read it. A terminal that claims in the same moment wins; a different document under the name is someone else's and revokes nothing. Removing the machine forgets its pending pickups. A terminal whose pickup did not complete has no credential and is refused `relay_auth_missing`; reopening it gives it a new one.

**Inside the terminal.** Every process the terminal runs inherits its credential and can act as its panel, as anything in a local c11 terminal can.

**After an update to protocol 2.** A terminal opened on another machine by an earlier build has no credential: its agents keep running, but their relayed calls are refused with `relay_auth_missing` until the terminal is reopened. The relay kit there must be reinstalled from the new build too: `c11 machine link --host <ssh-target> --update` (with c11's terminals there closed), or the install script below; until then its `c11` is refused with `relay_kit_outdated`.

**What authentication does not cover.** Stock hc lets any process of the same user on a machine type into, read and end every terminal there (hc's `docs/c11-to-hc.md`, R4.1). Such a process can still act as a c11 terminal's panel by reading that terminal's process environment (`ps eww`, `/proc/<pid>/environ`) or by typing `c11 ...` into it through the machine's hc socket. That is the same user's control of that machine, which the relay cannot be stronger than; closing it needs per-client authentication in hc or a per-host agent that checks the kernel's view of the caller (C11H-71). Also outside the relay's boundary: root on that machine, and the same user on the Mac (C11H-45).

## Mail

c11's envelope v1 stays the on-host format. `mailbox send` builds its envelope as it does locally and hands it to c11, which writes it into the recipient workspace's outbox for the normal dispatcher. The envelope must carry the CLI's sender claim naming the verified caller, and its `from` (and any `reply_to`) must be the caller panel's `mailbox.address` (as c11's own metadata has it), else `id:<its uuid>`; anything else is refused (`relay_identity_refused`, `relay_sender_refused`). c11 keeps only that sender claim (the dispatcher turns it into `ext.c11_sender_panel_id` as for local mail), drops every other client `ext` key, and adds `ext.c11h = {origin_host, machine, relay: true}`. `ext.cbus` is reserved for the bus and never written. A mail address is the panel's `mailbox.address`, else `id:<uuid>`; a `--to` that starts with a machine or host name and `/` or `:` is refused (`relay_host_prefix`): the host is a badge, never part of an address. Mail between two local panels is unchanged.

`mailbox recv` reads the caller's own inbox in two steps: c11 returns the unread envelopes without claiming them, the CLI prints them, then acknowledges the ones it printed, and only those are marked read. A link that drops between the steps leaves the mail unread, to be shown again; recv then exits nonzero with `relay_ack_failed: printed N, not acknowledged; they will show again`. `--ack` (or a terminal on stdout) is still required to mark mail read. `--body-ref`, `inbox-dir`, `outbox-dir`, `trace`, `tail` and `view` refuse over the relay: they name files on the machine c11 runs on.

## Install on the build host

Run on the build host, beside ticket 11's pinned hc, with the c11 CLI from the same build as the app (`c11.app/Contents/Resources/bin/c11`):

```bash
scripts/c11-atlas-relay.sh install --session c11 --cli /path/to/c11.app/Contents/Resources/bin/c11
```

Add Machine and `c11 machine link` run the same installer there, on a Mac or a Linux machine: they send the CLI for that machine with the app's `Info.plist`, Claude wrapper, note files and `c11` skill around it, laid out as the app is, so a fresh kit gets `bin/claude` too.

It writes only these files in `~/.local/share/c11/relay/<session>/`: the kit `c11-relay.app/` (`Contents/Resources/bin/c11`, the CLI binary, and, when they sit beside `--cli` in the app, its `Info.plist`, its `c11` skill, its Claude wrapper and note files, laid out as an app so `c11 guide` there names this build), `bin/c11` and `bin/c11h` (the kit's CLI in relay mode), `bin/codex`, the four `zdotdir/` startup files, `no-socket`, `manifest.json`, and with the Claude wrapper `libexec/claude` and `bin/claude` (below). The manifest's `files` lists them, `file_sha256` records what each was when written, `self_sha256` is the manifest's own hash, and `kit_version` names the kit's build. They are the only files install and `uninstall --session S` ever write or remove, and only while each still matches its hash; a reinstall refreshes the kit and removes kit files the new build no longer brings. A reinstall from a standalone CLI (not inside the app) refreshes only the CLI and keeps the kit's `Info.plist`, skill and Claude wrapper as the last app install left them, while they are still its own; if the wrapper is no longer its own, the Claude entry and a `bin/claude` it wrote go too, so nothing it owns names a removed file. An edited manifest owns nothing: install refuses, and uninstall removes nothing.

- **Files it didn't write:** anything else in the folder stays in place, except a `bin/claude` (below). So does a file at one of its own paths that was replaced or edited since, or that is a symlink. Install refuses symlinked parent directories too; uninstall never follows them. Install and uninstall each print a note naming it.
- **A conflicting file:** install refuses if one of its own paths holds a file that isn't its own. With `--shards`, every requested shard is checked first, so a conflict in one leaves all of them as they were.
- **Older manifests:** a manifest written before `files` existed owns the original eight paths (without `bin/codex`), and its `libexec/c11` is still checked against `cli_sha256`. Only a manifest with none of `files`, `file_sha256` or `self_sha256` counts as one. A legacy Codex shim is adopted only if it matches the generated bytes; a current manifest with any of them removed owns nothing. `libexec/c11`, where the CLI lived before the kit, is retired: an install removes it, while it is still its own, after the new shims are written.
- **Shards:** `--shards N` (1 to 8) acts on the shard sessions `S-s1` to `S-sN`, each with its own folder and manifest.

When the link comes up, c11 reads the manifest. Every terminal c11 then starts on that machine gets `ZDOTDIR` (the relay's zsh startup files, which source the user's own and then put the relay `c11` first on PATH, after path_helper and Homebrew) and `C11_SOCKET_PATH` / `CMUX_SOCKET_PATH` pointing at `no-socket`, so another `c11` binary (c11's own, an older one) fails closed with "Socket not found" instead of reaching the build host's c11. ZDOTDIR stays set inside that terminal, so an agent's own shells resolve the relay `c11` too. Shells other than zsh get the fail-closed socket path but not the relay on PATH. Terminals started before the install, and shells outside c11, are unchanged.

## Claude on the build host

A Claude in a c11 terminal there gets c11's per-launch hooks file and note, as a local one does. The installer writes `libexec/claude`, which runs the kit's copy of the app's Claude wrapper. It always writes `bin/claude`, which only runs `libexec/claude`: the kit owns that path. A `bin/claude` it did not write is moved to `set-aside/claude.<date-time>` in the same folder, byte-identical, and the installer prints one line saying so; it is never kept in front of c11's wrapper. (On 2026-11-03 a hand-written one that exported an account token outlived that account, and every Claude launched from c11 on that machine answered "You've hit your weekly limit".) The wrapper runs the next `claude` on `PATH` outside the relay folder, so an account choice or pool shim belongs there; whatever it exports reaches Claude unchanged, and c11 never reads it. When the kit carries no Claude wrapper, a `bin/claude` you wrote stays, and an install or uninstall that keeps it says so when it still runs the removed `libexec/claude`: point its last line back at your own `claude`.

The wrapper takes relay mode from the terminal itself: `C11_RELAY_BIN` (which c11 gives every terminal on a relay machine) naming a relay `bin/` with its `c11`, plus the terminal's `HC_TERMINAL_ID` and `C11_PANEL_ID`. The hooks file (in `$TMPDIR`; nothing in `~/.claude`) runs `$C11_RELAY_BIN/c11 claude-hook …` and hooks only the turn and attention edges: SessionStart, UserPromptSubmit, Stop, StopFailure, Notification, SessionEnd, and Pre/PostToolUse for AskUserQuestion and ExitPlanMode (so a question reads blocked). All are async except Stop and the ask answer. Each edge is one journal event with no session id, which c11 attributes to the panel's hc owner; the relayed hook writes nothing on that machine. Claude fires no hook when Escape interrupts a turn, so hc's idle, dated after the last hook edge on that machine's clock, ends a turn the hooks left working (never an open question). A real turn-end Stop (never a Stop-hook continuation) first drains the panel's mail: peek, write to Claude, then acknowledge exactly what was written, so a dropped link claims nothing and a failed acknowledgement shows the mail again. Every relay call's reply wait is cut to what the hook has left, so a Stop answers within Claude's 10 s. Not carried: conversation resume, completion notifications, the Running/Idle sidebar chip, the SessionStart orientation nudge, PermissionRequest, the native mailbox bridge, per-tool and subagent observations. Mail that arrives while the agent is idle still rings on hc's idle edge, as before.

## Show (C11H-228)

`c11 show` is the relay's one panel-creating verb (`show.open`, `show.close`). c11 places the viewer beside the verified caller and nowhere else: a relayed show carrying any panel, area, workspace, window, `machine`, `on` or `container` parameter is refused `relay_target_refused`. The path is read on the caller's verified machine, through c11's own hc session (`machine.exec` with fixed literal argv and no shell: `realpath`, `stat` and `cat`, each with `--` before the absolute path; symlinks resolve where the file lives and `--dir` assets must stay inside the folder). A caller inside an Incus container is read through `incus exec <container> --`, the container taken from hc's own foreground facts about the caller's terminal, never from the request: the process is `incus` (by name, so a `linux-seat` launch with `exec -a <harness>` counts) running `exec <container> …`. A point-and-say screenshot for such an agent is pushed into its container (`/tmp/c11-show/shots/`); a screenshot is only ever taken of the shown page or another page of the same source, never of a page the viewer wandered to (C11H-247). The relay session's `machine.exec` and `file.write` accept only these shapes (`ShowExecGate`): `realpath`, `stat` with its fixed format options, or `cat`, each with `--` before an absolute path and optionally behind `incus exec <container> --`; the screenshot push; removing a shot; and writing a shot under `~/.local/share/c11/show/shots/`. A URL from a linked machine may not be `file:`, any loopback spelling or the operator's Mac's own names and addresses. Every `browser.*` and `markdown.*` method stays refused, with the hint to test on your own machine and `c11 show` the result.

While c11 is away the CLI writes the show into its own machine's hc document `c11h.show.<panel-uuid>`, each entry signed with the terminal's relay credential, and exits 0. c11 reads those documents at link-up, on their `doc` events and on resubscribe, for panels whose terminal runs on that machine now, and surfaces only entries that terminal signed: each becomes one Feed row (`noticed` in the document, so a restart rebuilds the same row). The operator opening that row opens the viewers; nothing opens unasked. A container caller's record needs `linux-relay-proxy` to pass `doc.get`/`doc.set` on `c11h.show.<panel>` for that container's own panels; without it `show` from a container works only while c11 is answering.

## Linux machines and workspace containers (C11H-191)

The relay kit runs on a Linux machine too: the same installer with the CLI built for x86_64 Linux (`tools/linux-cli/`), plus the app's Claude wrapper and note, laid out as the app is. Where Linux lacks `uuidgen` and `plutil`, the wrapper, its note and the Codex shim fall back to the kernel's uuid and a plain read of `Info.plist`. bash never reads `ZDOTDIR`, so the kit also writes `bash/rc` and its manifest names it: when a terminal's shell is bash (a Linux machine's link bakes `SHELL=/bin/bash`), c11's launch line starts `bash --rcfile <kit>/bash/rc -i`, which reads what a login bash reads (`/etc/profile`, then the first of `~/.bash_profile`, `~/.bash_login`, `~/.profile`) and then puts the relay `bin/` first on PATH, keeping it first after prompt hooks: its fixer runs after the hooks the user's files registered, at every prompt (the last element of an array `PROMPT_COMMAND` on bash 5.1 and later). That shell is interactive but not a login shell: `logout` asks for `exit`, and `~/.bash_logout` is not read. A kit installed before `bash/rc` leaves bash's PATH as the machine sets it. `C11_RELAY_BIN` and the credential pickup work as on the build host, because the launch line is plain `sh`.

**Agents in containers.** The Linux host runs each c11 workspace's agents inside Incus containers that its `linux-seat` enters from the c11 terminal (Stage 11 `platform/linux-starmind`). A container never gets the machine's hc core socket, which would let it start or type into any terminal there. Instead `linux-seat` gives each container its own relay socket, served by `linux-relay-proxy` on the host, at the path the kit's shim names. The proxy passes the client's `hello`, `doc.get` and `doc.set` on the relay slots and `doc.get` on the heartbeat, and nothing else: no spool, no credential pickup, no other method. A request must name a panel that entered that container; a slot another container holds reads back as occupied, with its age only, and cannot be written or freed. The credential still decides who the caller is; the proxy keeps containers apart below it, so a container cannot act for another workspace's panels or read their replies and mail. `linux-seat` hands the container the kit read-only and id-shifted (the kit is owner-only on the host; inside, its owner is the container's agent), the terminal's credential as a 0600 file in `/run/agent/relay/` (never argv or the container's config), and puts the relay `bin/` first on PATH, so the agent's `c11`, `c11` and the Claude and Codex wrappers work as on the build host. Telemetry cannot spool from a container: while the link is down, `set-status` and the other spoolable calls fail instead of queueing.

**The foreground.** The terminal's foreground on the machine is the `incus exec` client. `AgentDetector` reads the command right after `incus exec <container> [options] --` as the harness (never its arguments), and a launcher that wraps the harness in a shell, as `linux-seat` does, names it as the client's argv[0] (`exec -a`), which any build reads. Either way the panel is an agent to c11: the remote doorbell rings for it and hc's turn edges count.

**Taking effect.** c11 reads a machine's relay manifest when its link comes up. After the kit is first installed on a machine, terminals opened there get the relay from the next link-up (a c11 restart, or the link reconnecting); terminals opened before keep running without it.
