## Apply by default

### Blockers (plan is not yet executable as written)

- **B1: Step 2 specifies building a probe that already exists in production**
  - Where in the plan: Step 2 — "Add a testable linked-worktree probe that compares `git rev-parse --git-dir` with `--git-common-dir` and captures the branch name."
  - Problem: `Sources/Metadata/GitContextResolver.swift` already performs exactly this comparison (line ~336-340), with absolute-path normalization before comparing, an injectable `GitRunner` seam for deterministic tests, a bounded `ProcessGitRunner`, outer-superproject-before-inner-submodule resolution, and a `GitContextKind` that models `mainCheckout` / `linkedWorktree(basename:absolutePath:branch:)` / `stale`, plus a `BranchValue` enum with `.attached` / `.detached(shortSHA:)` / `.noBranch`. **Verified: all of these exist as cited.** A second detector will re-derive the easy half (the string comparison) and silently drop the hard half (normalization, submodules, stale worktrees, detached HEAD, timeout), and the two will drift on the next fix.
  - Revision: Rewrite step 2 to consume `GitContextResolver` (or extract a shared, strictly-bounded classification primitive from it) through a thin pure policy adapter. Do not author a second `--git-dir`/`--git-common-dir` comparison. If measured launch latency forces a narrower dedicated probe, the plan must say so explicitly and state that it derives from the same shared path/branch primitives.
  - Sources: standard-codex (Weakness 1, blocking); standard-gemini (Architectural Assessment note); adversarial-claude (Finding 1, "the plan proposes building something that already exists"); adversarial-codex (P1 #2); evolutionary-codex ("Build on the Git capability that already exists"). - **B5: Probe-failure policy, timeout budget, and degraded git states are unspecified**
  - Where in the plan: Steps 2-4 treat the git classification as an infallible boolean.
  - Problem: The production git runner is subprocess I/O with a per-call soft timeout; the CLI's socket deadline is separate and shorter than a worst-case multi-call resolve. `git` may be absent from the app-process PATH (`docs/launch-agent-reference.md` explicitly warns "the app-process PATH is poorer than the login-shell PATH a pane actually gets"), the directory may not be a repo at all, the worktree may be `.stale` after a sibling ran `git worktree remove`, and the resolver's failure modes currently collapse to `nil`. Fail-open silently restores the exact silent failure the ticket targets; fail-closed on an inconclusive probe breaks legitimate launches. Neither is chosen. A probe that outruns the client deadline can also produce a late launch after the caller has already been told it failed, which an orchestrator retry then duplicates.
  - Revision: Add a decision table with an explicit outcome per state — non-repo, main checkout, linked worktree (attached), linked worktree (detached), linked worktree (no branch), stale worktree, git executable missing, permission failure, timeout — resolved **separately for inherited and explicit cwd**. Pre-register an end-to-end latency budget below the socket deadline, and state that a timeout is terminal before any mutation (no late launch). Reviewers lean fail-open-with-a-visible-warning on an indeterminate inherited probe as the proportionate default; whichever is chosen must be written down as a deliberate contract rather than an implementation accident.
  - Sources: standard-claude (Weakness 2, timeout/PATH/non-git-directory); standard-codex (Weakness 7); adversarial-claude ("Fail-open vs fail-closed is left undecided, and both answers are bad", Q6); adversarial-codex (P1 #5); adversarial-gemini (Blind Spots, "Timeout and Fallback", Q3); evolutionary-codex ("Define degraded behavior"). - **M2: State the guard's honest scope — it is a tripwire, not an enforced invariant**
  - Where in the plan: Implicit throughout; the ticket frames this as enforcing "no two agents mutate the same tree."
  - Problem: This guard cannot deliver that invariant, and reviewers converged on saying so plainly. It allows main checkouts (two agents in one checkout is the same bug), allows explicit overrides, allows multiple explicit helpers in one worktree, allows non-git directories, and is entirely blind to an agent that `cd`s elsewhere one second after launch. Git records topology, not ownership or liveness, so the guard cannot actually prove a linked worktree belongs to *another* agent. Overselling it invites a future reader to believe they are protected when they are not.
  - Revision: Add one framing line and one non-goal. Describe the deliverable as a high-signal guard against *accidental inherited* launches into a linked worktree, and add "post-launch `cd` into a contested tree" plus "main-checkout collisions" to the non-goals. Ensure the user-facing error copy makes the same limited claim.
  - Sources: standard-codex ("The Plan's Intent vs. Its Execution"); adversarial-claude ("The Uncomfortable Truths"); adversarial-codex ("The Uncomfortable Truths"); evolutionary-claude (Mutation 5). Four reviewers.

## Surface to user (do not apply silently)

- **S1: Does a C11-194 workspace root count as explicit intent or as an inherited default?**
  - Why deferred: disagreement + design-needed
  - Summary: Once C11-194 lands, cwd precedence is explicit `--cwd` → workspace root → launching-surface cwd. An operator may deliberately configure a workspace root that *is* a linked worktree — entirely reasonable when a workspace exists to work one branch. The plan's binary explicit/inherited framing has no slot for "configured." Reviewers split cleanly: standard-claude argues "strongly it must be allowed, since the operator explicitly configured it"; adversarial-codex argues the opposite, "the answer should be yes [guarded] unless the operator explicitly supplied `--cwd`"; evolutionary-gemini says it "logically should" act as an explicit override; standard-codex and evolutionary-codex raise it as an open question without taking a side. The mechanical fix is the same either way — the provenance enum from B2 needs a `.workspaceRoot` case — but which side that case falls on is a product decision the plan author or operator must make.
  - Sources: standard-claude (Q14); standard-codex (Q1); standard-gemini (Weakness 2, Q2); adversarial-claude (Q15, Reality Stress Test #1); adversarial-codex (Challenged Decisions, Q2); adversarial-gemini (Q4); evolutionary-codex (Q1); evolutionary-gemini (Q1, Suggestion 3).

- **S2: The guard will fire on this repo's own dominant workflow, and there is no escape hatch**
  - Why deferred: design-needed + disagreement
  - Summary: `git worktree list` reports 39 entries (38 linked) in this checkout — **verified** — and the house `lattice-orchestrator` workflow mandates one worktree per delegator. A delegator launching its own reviewer/translator/validator from its own worktree is the sanctioned, dominant launch shape, and the guard as specified refuses it. The classic failure arc follows: the guard misfires on the common case, `--cwd` becomes a reflex in every prompt template, and the guard's fire rate silently goes to zero while looking identical to a working guard. Reviewers proposed three different remedies and did not converge: (a) an explicit `--allow-worktree` / `--force` flag, following the repo's own established idiom at `pane.create`'s `--allow-undersized`/`--force` (standard-claude, adversarial-claude, evolutionary-claude); (b) replace the linked-worktree proxy with the precise signal — c11 already stores `MetadataKey.worktree` per surface and knows every live surface's cwd, so "is another *live surface* already rooted in this tree, and is it not me?" needs no subprocess, has near-zero false positives, names the offending surface in the error, and extends to main-checkout collisions (adversarial-claude, evolutionary-claude); (c) ship warn-only with a counter for one week using the existing `AgentLaunchStatsStore` and let the measured false-positive rate settle the question (adversarial-claude, evolutionary-claude). standard-codex and standard-gemini consider the guard acceptable as scoped. None of these is a small in-place edit, and (b) in particular would change the guard's shape rather than its plumbing.
  - Sources: standard-claude ("The ergonomics question nobody asked", Q12); adversarial-claude (Finding 3, "How Plans Like This Fail", Blind Spots, Q4/Q5/Q9/Q19); adversarial-gemini (Assumption Audit); evolutionary-claude (item 3, Mutation 1); evolutionary-codex ("From heuristic to lease-aware ownership").

  - Why deferred: author-intent-needed
  - Summary: The ticket's stated case for a guard over a better default is one sentence: a guard "also holds when someone passes `--cwd` explicitly, which a default cannot." The plan's step 3 then explicitly permits `--cwd` into a worktree with a one-time acknowledgement — which removes the very property that justified a separate ticket. adversarial-claude argues two coherent positions exist (enforce on both paths with a real `--allow-worktree` override, or admit this is a loud default and fold it into C11-194) and the plan picks neither. adversarial-gemini raises a related but distinct objection: that a git-workflow-specific guard in the general-purpose c11 binary violates the repo's own "unopinionated about the terminal" principle, and that the check belongs in the `lattice-orchestrator` skill instead — a single-reviewer strategic claim that the ticket's own reasoning contradicts, included here only because it bears on the same "should this exist in this form" question. Every other reviewer endorsed server-side enforcement as the correct boundary. This needs the plan author's or operator's call, not a silent edit.
  - Sources: adversarial-claude (Executive Summary "the single biggest issue", Challenged Decisions, Q20, "The Uncomfortable Truths"); adversarial-gemini ("The Uncomfortable Truths", Q6).

- **S5: A pure-filesystem probe was proposed as an alternative to reusing `GitContextResolver`**
  - Why deferred: disagreement with B1's consensus direction
  - Summary: A minority of reviewers argued for skipping git entirely: a linked worktree has a `.git` *file* rather than a directory, so a walk-up reading `.git` and `<commonDir>/worktrees/<name>/HEAD` needs no subprocess, no timeout, no PATH dependency, and is trivially pure-logic testable against temp-directory fixtures — which is what steps 4 and 5 promise. The counter-consensus (five reviewers, B1 above) is that `GitContextResolver` already ships an injectable `GitRunner` seam that makes pure-logic testing possible *with* reuse, while also handling submodules, stale worktrees, bare clones, and branch-state modeling that a hand-rolled filesystem walk would have to re-derive. A hybrid was also floated: stat to decide, git only to name the branch. This only becomes live if measured launch latency makes the resolver's multi-call path unacceptable on the launch hot path — which nobody has measured.
  - Sources: standard-claude (Alternatives Considered, "Shelling out to git versus reading `.git` directly"); standard-gemini (Alternative 1); adversarial-gemini (Challenged Decisions); evolutionary-claude (item 2). Counter-position: the five B1 sources.

- **S6: Adjacent latent bug found during review — file separately, do not fold in**
  - Why deferred: scope-creep (out of scope for this plan)
  - Summary: `v2AgentLaunch` computes `let lookupCwd = cwdOverride ?? FileManager.default.currentDirectoryPath` (`Sources/SocketHandlers/SocketDispatch.swift:1073` — **verified**) and uses it to find `.c11/agents.json` via `DefaultAgentProjectConfig.find(from:)`. That fallback is the **c11 app process's** cwd, which for a GUI app is essentially arbitrary, so project-level agent configuration is silently not applied on the default (no-`--cwd`) path. The same pattern reportedly appears in `defaultAgentLaunch` in `TerminalController.swift`. Same root cause as B2 (the launching surface's cwd is never plumbed to the server), and C11-194's centralization is the natural place to fix it — but it is a distinct bug with its own user-visible symptom and deserves its own ticket rather than quietly riding along.
  - Sources: evolutionary-claude (item 8, Q11); corroborated as an assumption-audit item by adversarial-claude (A2c). Independently verified.

## Evolutionary worth considering (do not apply silently)

- **E1: Stamp the git tree and branch onto the surface instead of discarding them**
  - Summary: Whichever detection method wins, the launch path will — for the first time — know a surface's git tree and branch at birth. All three evolutionary reviewers independently proposed persisting that fact (`git_root`, `git_branch`, `git_worktree_kind`) as surface metadata via the existing identity-at-birth stamping, rather than consulting it for one boolean and throwing it away. The delta is one field on the return type plus one call the launch path already makes.
  - Why worth a look: it is the input to `c11 tree` showing branch-per-agent, to collision telemetry, to the precise "another live surface holds this tree" rule in S2, and to auto-worktree provisioning — none of which are answerable today.
  - Sources: evolutionary-claude (item 4, "The Flywheel"); evolutionary-gemini (Suggestions 1 and 2); evolutionary-codex ("A launch-context receipt", Concrete Suggestion 9).

- **E2: Ship warn-and-count before flipping to refusal**
  - Summary: Split the change at a boolean: release the probe, the metadata, and a warning through the existing `warnings` array with a counter through the existing `AgentLaunchStatsStore`, run it for one week of real fleet use, then flip warn to refuse. The split costs almost nothing (same diff, one branch) and would produce the false-positive rate as a number instead of an argument.
  - Why worth a look: it settles S2's proxy-versus-precise-rule debate empirically, on a machine with 38 live worktrees where the operator personally eats the cost if the rate is high.
  - Sources: evolutionary-claude (Mutation 1, Sequencing steps 2-3); adversarial-claude ("Why didn't we just measure first?", Blind Spots).

- **E3: `--worktree new` — provision the tree instead of policing it**
  - Summary: Every delegator in the lattice-orchestrator workflow does the same manual three steps: `git worktree add`, provision submodules plus the GhosttyKit symlink (CLAUDE.md documents this as a known first-build trap), then launch the agent there. A flag like `c11 launch-agent --type codex --worktree new --branch feat/C11-201 --new-workspace` would create the worktree from the workspace root, run a declared provisioning hook, and launch with cwd set to the fresh tree.
  - Why worth a look: agents land in each other's trees because getting their own is manual — this removes the failure mode rather than detecting it, and C11-193's probe plus C11-194's workspace root are exactly its two prerequisites.
  - Sources: evolutionary-claude (Mutation 2, Sequencing step 5); adjacent to evolutionary-codex ("Explain without launching", general launch-policy hooks).
