## Finding: pre-existing stamp phase can run too early

The build-host's actual current `$HOME`-owned tag build log (`/tmp/c11-xcodebuild-val-3.log`) places app `PhaseScriptExecution Run Script` at line 233, then app `ProcessInfoPlistFile` at line 810. The script stamps `${TARGET_BUILD_DIR}/${INFOPLIST_PATH}` only when the file already exists. Xcode subsequently generates the product Info.plist from `Resources/Info.plist`, which contains no C11Commit/CMUXCommit. Thus a fresh product can skip stamping, and an existing stamped product can be overwritten by the later plist task. The final packaged Info.plist indeed contains version `0.67.0`, build `131`, and neither commit key.

This is an actual packaging ordering weakness, not evidence that Debug intentionally never stamps. The existing stamp block has no Debug exemption. Git history places the C11Commit phase under earlier branding commit `6d0bc1a843` (#37), before C11-284. `scripts/reload.sh` retags/re-signs after xcodebuild and does not re-add C11Commit; the nightly workflow independently stamps both commit keys after building. No build, plist edit, new stamp, source change or signing change was performed for this diagnosis.

## Contract: nullable commit is represented honestly

C11-284's ticket explicitly accepts version plus git SHA **or build stamp**. `Sources/BundledSkill.swift:3` confines identity to the built bundle, models commit as optional, prints version/build even without a commit, and returns unknown (`nil`/JSON null) from commitsMatch when either commit is unavailable or malformed. CLI capabilities help at `CLI/c11.swift:8684` says sha_match is null when either build lacks a stamp. This runtime supports an unstamped bundle honestly; that fallback does not imply the packaging ordering weakness is desirable.

The stock `tests_v2/test_guide_and_features.py:83` imposes a stricter non-null commit assertion, then its synthetic-case construction calls `.startswith` on that assumed non-null value. That fixture rejects a permitted build-stamp identity. The ignored `C11-284-nullable-runtime.py` changes only the fixture assumptions: require version/build and its printed header; retain actual commit null; compare null/missing/valid/invalid/empty synthetic peer commits with the expected unknown result. It does not mint a fake stamp, edit the app, or replace shipping source.
