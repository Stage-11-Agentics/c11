# Cutting over from c11h to c11 2.0

One page for moving a Mac that runs c11h day to day onto c11 2.0 without losing a panel. On the
operator's own Mac this runs only on his go. How it works: the C11H-266 and C11H-283 plans in the
private ops repo (`c11-ops`, `notes/c11-2.0/`).

## What happens

On its first launch, c11 2.0:

1. Quits c11h if it is running, the same way Cmd-Q does. Every terminal keeps running, detached.
   If c11h takes longer than a second, a small c11 window says c11h is still quitting, and c11 opens
   by itself once it has. If anything stops the move, the same window says what happened and that
   c11h's own files are untouched; c11 does not open on a half-moved world.
2. **Adopts** c11h's world in place while any c11h terminal is alive. Every agent and shell stays
   in its terminal, and the panel is the same, with the same process and scrollback. The agents keep
   c11h's environment, so c11 2.0 serves c11h's socket path and mailbox folders as its own. c11h's
   settings are copied into c11's settings. c11h's own files are never edited.
3. **Converges to c11's own names** on a later launch once every adopted terminal, holder and linked
   machine is proven absent. It copies the latest saved state into four real c11 directories. Saved
   conversations recover through the ordinary resume policy once; repeated launches do not resume them
   again. An uncertain liveness check stops the move. An interrupted move is reconciled from the actual
   directories on the next launch, and c11 opens only after the complete layout is verified.
4. Keeps c11 1.x's state aside, if the Mac has one, before anything else: its settings are exported
   and its folders moved, whole, into `~/Library/Application Support/c11-1.x-kept-<date>/`. `KEPT.md`
   in that folder says how to put them back.

Every step writes one JSON line to `~/Library/Logs/c11/migration.log`.

## Before

- **C11H-283 has landed and its guest proof has passed.** The operator's own cutover waits for this gate.

- **The Constellation Bus's c11 adapter must not depend on c11h's paths.** It names
  `/Applications/c11h.app` and `Application Support/c11h/c11h.sock`. Before cutting over, either CBUS-78
  and CBUS-85 have rolled out on that Mac (ask the Bus Lead, mailbox `bus-lead`), or run
  `wiring/delivery/switch.sh off` in the constellation-bus repo, which holds mail without losing it
  until the adapter is updated.

- Run c11h 1.8.1-h11 or later. Cores of h11 to h15 are adopted without a restart.
- Keep `/Applications/c11h.app` installed. The adopted terminals run its hc helper, and their `PATH`
  points into it. Remove it only after convergence.
- Save a record to compare against afterwards:

  ```bash
  c11h hc-diagnostics --json > ~/c11h-before.json
  c11h tree --all --json > ~/c11h-tree-before.json
  ```

## Cut over

1. Install c11 2.0 at `/Applications/c11.app`. This replaces c11 1.x if it is still there.
2. Open c11 2.0. Do not open c11h again while c11 2.0 runs.

## Check

- `tail ~/Library/Logs/c11/migration.log` shows `"step":"plan"` with `adopt`, then `"step":"adopt","outcome":"ok"`.
- `c11 hc-diagnostics --json`: every panel in `~/c11h-before.json` is listed and `live`, with the same
  `terminal` and `pid`.
- Every workspace is in the sidebar, including the hidden ones, with its titles, colors and descriptions.
- After convergence, the log shows `"outcome":"converged"`; Application Support/c11, `.c11`,
  `.c11-snapshots` and `.config/c11` are real directories, and newly recovered terminals use c11's pool.
- In a panel that was running before, `c11h mailbox send --to <address> test` reaches its recipient.
  Mail sent to that panel arrives.

## Linked machines (the build host, the Linux host)

**Before cutting over, let the agents on linked machines finish, or stop them.** Their terminals keep
running after the switch, but c11 2.0 opens nothing new through the link c11h made, and those agents'
c11 calls and mail are refused.

Machines are linked in c11h's own hc sessions, so adopting those sessions brings the links and remote
terminals along. A c11h-era link doesn't check c11's hc, and c11 can't make it check one without
trusting the hc file already on that machine, which is the thing the check exists to verify. So c11 2.0
won't open terminals through it. What the guest runs proved (C11H-274 and C11H-391; a Mac and a Linux
machine, each linked by c11h):

- **Running remote terminals stay attached and work** (Mac and Linux): same process, live output, typing
  reaches them. `c11 machine audit` shows `link unusable`, code `via_outside` (Mac and Linux).
- **Its agents' c11 calls and mail are refused** (Mac; the Linux machine had no relay kit):
  `relay_link_unusable: c11 won't use this machine's link: it doesn't check c11's hc and c11 couldn't
  update it. Update or Remove the machine in Settings > Herder Topography.` hc may still redial the link.
- **Nothing new opens there through c11h's link** (Mac): until the machine is linked again,
  `c11 new-panel --on <machine>` and `launch-agent --on` exit nonzero with `machine_link_unusable`, and
  the New Terminal picker lists the machine but won't pick it. The refusal is by machine name, with no
  platform check (`HCMachineTarget.resolve`), but the Linux case was not run.
- **Splits that would start a terminal there are refused too.** `c11 new-split` of one of its
  terminals answers `machine_link_unusable` (Mac, run in the guest). The keyboard split (Cmd+D), the
  menus and the panel bar's split buttons create nothing, beep, and say why in a note over that
  terminal (Cmd+D run in the guest; the menus and the panel bar tested in code). A workspace apply
  (`c11 restore`, a blueprint) leaves out each terminal there, reporting it as `machine_link_unusable`,
  and makes every other panel; an area left empty goes, and a plan with nothing else fails before any
  workspace exists, so an in-place restore keeps the workspace it would replace (tested in code).
  Dragging a panel beside one of its terminals moves it, since a move starts nothing there (run in the
  guest); only dragging an area's last panel, when it is one of that machine's terminals, to that
  area's own edge is refused, since c11 would refill the emptied side on that machine, with the same
  note (run in the guest). A refusal an agent's socket call
  meets (`new-split`, `drag-panel-to-split`) is the agent's error to read, with no note on the Mac (run
  in the guest) and no sound (C11H-396). All of this lasts until the machine is linked again.

### Link the build host again, while adopted

c11 2.0 links machines in a session of its own (`c11`; `c11-<tag>` on a tagged build), beside the
adopted c11h sessions, so Add Machine works while c11h's terminals still run. Proved in a guest for a Mac
(C11H-391), except where marked:

1. Settings ▸ Herder Topography ▸ the machine's gear says c11h linked it and offers **Link Again…**,
   which opens Add Machine for the same name and SSH target, through the consent screen. Every step
   passes. It installs c11's own hc there, checked against this build's hash, under
   `~/.local/share/c11/`, with its state in `~/.local/state/herdr-core/c11/`. The new link writes nothing
   in c11h's folders there, and c11h's hc and terminals there keep running, same process.
2. From then, new terminals on that machine open through c11's link: `--on <machine>`, and a split of a
   c11h-era panel there. Typing reaches them; mail sent from one reached a recipient that read it with
   `c11 mailbox recv --ack`, and `c11 set-status` from one set the workspace's status. `--on` and
   `c11 new-split` are refused with `machine_link_unusable` only while no link of that name is usable.
   (The picker, the File menu and the panel bar's split make the same choice; tested in code, not run
   in the guest.) For a few seconds after launch, before c11's own session has reported, `--on` to a
   machine it lists answers `hc_unavailable` where it would otherwise be refused (a usable c11h link
   still opens): retry. The c11h-era terminals stay as above.
3. Quitting and reopening c11 2.0 reattaches c11's terminals there, same process.
4. The gear then shows both links. **Remove c11h's Link…** lists the c11h-era terminals there, ends them
   with everything they started, and removes c11h's link. c11's terminals there keep running, same
   process, and keep sending mail and setting status. **Update…** for c11's own link appears beside
   them when that link needs it (tested in code). **Remove…** removes c11's own link (not run in the
   guest).

`c11 machine link --host <ssh-target> --name <machine>` and `c11 machine unlink --id <machine> --session
c11h` take the same paths from the command line. In the guest, `c11 machine link --update` from the
command line while adopted acted on c11's own link: it stopped, as Update does while terminals there are
open, and the audit names c11's session. A full link from the command line and `unlink --session` were
not run in the guest.

**Don't remove c11h's link while its agents are still working.** c11h's hc keeps running there with no
terminals, because c11 stops only an hc it installed (Mac and Linux). It holds no terminals, so it can
stay. To end it on the build host, stop its `herdr-core serve` and `herdr-core hold` processes (running
from `~/.local/share/c11h/hc/`) by process id. On the Linux host, hc 0.1.16 starts them as
`systemd-run --user` units named `hc-serve-*` and `hc-hold-*` when a user manager runs (hc's
`crates/herdr-core/src/platform/systemd.rs`): stop them with `systemctl --user stop <unit>`.

### The Linux host

Add Machine accepts an x86-64 Linux machine (C11H-392). It checks linger and the user-service file
limit first and names the command for each, and installs c11's own Linux hc there, never the one
c11h's links use. C11H-392 proved it once 2.0 had converged. While adopted, **Link Again…** for the
Linux host takes the path above for the build host, into c11's own session, but no guest has run that
for a Linux machine. Until it is linked again, the Linux host keeps only c11h's link: its terminals keep
running, and nothing new opens there.

### Convergence

While any c11h session still lists a linked machine, or a c11h terminal or hc core lives on this Mac,
c11 2.0 stays adopted, even across a reboot. A link c11 2.0 made while adopted does not hold it there:
it is already in the session c11 converges to. So:

1. When the agents on a machine are done, remove c11h's link: **Remove c11h's Link…** when c11's own
   link of that name exists, else **Remove…**.
2. Let this Mac's c11h terminals end: a reboot ends them and c11h's hc cores.
3. The next launch converges (the migration log shows `"outcome":"converged"`). Terminals on a machine
   c11 linked while adopted reattach, same process, and new ones open there as before. Nothing is
   linked again.

Proved in a guest for a Mac (C11H-391), in this order: c11h's link removed while c11's own link of the
same name ran a terminal there; this Mac's hc cores ended, as a reboot does; c11 2.0 converged; c11's
terminal there reattached with the same process. That same terminal sent mail, which the recipient
read, and set the workspace's status, after c11h's link was removed and again after convergence.
Removing machines in c11h before cutting over is not proven.

## Going back

While c11 is still adopted, its original c11h files remain available:

1. Quit c11 2.0 (Cmd-Q). Its terminals keep running.
2. Open c11h. It finds its own workspaces and the same terminals, including its terminals on linked
   machines (proved for a Mac, C11H-391). A terminal c11 2.0 opened through its own link is not shown in
   c11h, but keeps running there and reattaches when c11 2.0 opens again (proved for a Mac). A c11h link
   removed in c11 2.0 is gone from c11h too, since the removal is made in c11h's session (not run).

Never run c11h and c11 2.0 at the same time: both would attach the same terminals. Mail and changes
made while c11 2.0 ran stay in the shared mailbox folders, so c11h sees them too. Opening c11 2.0
again later resumes where it left off and migrates nothing twice.

After convergence, c11's directories are authoritative and c11h's retained files are a separate older
world. Returning to c11h does not include changes subsequently made in c11, and later c11 launches do
not copy that older world again. The diagnostic setting `C11_MIGRATION_CONVERGE=0` holds adoption;
an unfinished convergence stops visibly until that setting is removed.

To give c11 1.x back its state after convergence, follow `KEPT.md` in the kept folder.
