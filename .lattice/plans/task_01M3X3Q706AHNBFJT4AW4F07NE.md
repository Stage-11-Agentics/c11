## Binding model and ordering decisions

1. Window-local `WorkspaceGroup: Identifiable, Equatable, Codable, Sendable {id: UUID, name: String, color: String?, icon: String?, isCollapsed: Bool, isPinned: Bool}`. Ordered `workspaceGroups` belongs to WorkspaceManager; optional `Workspace.groupId` is the sole membership relation. No stored member list, parent group, anchor or hidden PTY. Duplicate display names are allowed; identity is UUID. Empty groups survive last-member removal/close.
2. Keep the existing flat `workspaces` array as the canonical order for list indexes, keyboard workspace shortcuts/cycling, restore selection and batch reorder. Group member order is that array filtered by groupId. Group order is a separate ordered array; it does not depend on a first member. This avoids changing all existing workspace indexes and focus traversal when a folder collapses.
3. Shared W1/W2 sidebar projection: pinned groups, pinned ungrouped workspaces, unpinned groups, unpinned ungrouped workspaces. Within each group, members follow canonical workspace order, which places individually pinned members first. Group pin controls the folder's root segment; member pin controls position within its folder and is retained when leaving it. Neither operation changes the other's bit. Thus a pinned member in an unpinned folder stays inside that folder. Group order changes only via group move/pin, not workspace reorder. No arbitrary interleaving of folder headers and ungrouped rows in this PR.
4. Batch `--order` is a nonempty, possibly partial priority list of existing workspace IDs. Within each global pin segment, requested IDs come first in request order; untouched IDs retain relative order. Membership and group order are unchanged. Individual moves use the same canonical pin bounds; before/after calculations remove the source before resolving insertion to avoid off-by-one moves. W2 membership transfers pass an explicit destination group/ungrouped target, then normalize placement within the destination member pin segment. Dropping across a pin boundary clamps the indicator and result; it never silently toggles pin.
5. `add` accepts currently ungrouped workspaces; duplicate entries, already grouped members (including the same group), unknown IDs, and wrong-window IDs return distinct errors before changing anything. Moving between folders is explicit `move --workspace ... --to-group ...`; `remove` detaches named members to ungrouped. `delete` and `ungroup` both remove the folder record and detach all members, retaining their canonical order, pins, tabs and live processes. This is deliberate non-destructive parity, documented in help.
6. Group focus keeps the selected member if already in the group; otherwise selects the first live member in canonical order. Empty groups return `empty_group` without creating a workspace. It may expand the group and select internally, never activate/raise macOS windows. All other group verbs preserve selected workspace, selected tab, responder and app focus, even collapse of the selected workspace's group.
7. Cross-window group operations are unsupported and return `wrong_window`; existing individual workspace move-to-window clears membership on detach, leaves the source folder intact, and attaches ungrouped using existing selection behavior. Closing a member does not delete or promote the folder. New workspaces start ungrouped; there is no ambient group inheritance.

## CLI/socket contract for W2/W3

All verbs accept `--window <window-ref|uuid>` and `--json`; mutations require explicit group/workspace targets. Omitted window follows the existing caller window resolution, not a search across windows. Group selectors are UUID or ephemeral `workspace_group:N`, never an ambiguous name/index.

- `workspace-group list`; `create --name <text>` creates an empty unpinned, expanded folder. `rename --group <g> --name <text>`; `delete|ungroup|collapse|expand|pin|unpin|focus --group <g>`.
- `add|remove --group <g> --workspaces <comma-separated-refs>` validates the entire array. `move --group <g> (--before <g>|--after <g>|--index <n>)` reorders folders within the folder's pin segment. `move --workspace <w> --to-group <g|none> [--before <w>|--after <w>]` transfers/reorders one member; target workspace must belong to that destination. Without relative placement append within its member pin segment.
- `set-color --group <g> (--color <hex>|--clear)` uses WorkspaceColorSettings.normalizedHex; `set-icon --group <g> (--icon <SF-symbol>|--clear)` validates a renderable symbol with folder.fill as the display fallback. Trim and reject empty names. Invalid text/property input returns `invalid_params` with no mutation.
- `reorder-workspaces --order <comma-separated-refs> [--dry-run]` calls `workspace.reorder_batch` with ordered_workspace_ids and dry_run. Result: window_id, dry_run, changed, final_workspace_ids and per-request from/to indexes. Apply computes against current input inside the same main-thread snapshot/commit turn; a preceding dry-run is advisory, not a stale-plan token.
- Socket methods are `workspace.group.<verb>` (hyphens become underscores) and `workspace.reorder_batch`. Group records expose id/ref, name, color, icon, is_collapsed, is_pinned, member_workspace_ids, member_count. Workspace records expose group_id (null when ungrouped). Error codes include invalid_params, duplicate_workspace, already_grouped, not_member, group_not_found, workspace_not_found, wrong_window, empty_group.

Parse syntax/arrays off main. Resolve authoritative window membership, take exact collection snapshots and apply UI-owned model mutations in one short v2MainSync turn, with a comment explaining that main execution is required for a synchronous UI collection result. Fifty/128-item linear planning is bounded; no telemetry handlers move onto main and no per-keypress scheduling is introduced.
