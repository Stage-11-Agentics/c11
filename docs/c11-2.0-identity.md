# c11 2.0 identity map (C11H-265)

Status: draft for the Prep Lead, Fri 2026-11-13. Prep only: nothing here publishes.

c11h's code ships as **c11 2.0** under c11's identity, so c11 1.8.x installs update into it. Every row
below gives the identity, its c11h value, its 2.0 value, whether the old value stays as a **hidden
alias** (works, never in help, skills or docs), the measured count (`git grep -c`, tracked files,
`notes/` excluded, on `origin/main` 3ea44974), and the ticket that owns the row:

- **265** (this ticket): the rename, done by `scripts/c11-2.0-rename.py` plus one commit of hand edits.
- **266** (seat `c11-2-migration`): what 2.0's first launch does with c11h or c11 1.x state. It codes
  against `C11Identity.Legacy` (row 0), the one place the old c11h names survive in Swift.

Measured surface: 11,552 `c11h` mentions (case-insensitive) in 375 c11h-named files. Of those,
2,016 are ticket ids (`C11H-123`) and stay; 961 are `C11H_*` variable uses (241 distinct names);
307 are `com.stage11.c11h`.

## The rule

1. **2.0 code uses only c11 names.** Every path, socket, session, bundle id, defaults domain, scheme
   and variable a 2.0 build writes is c11's. So a tagged 2.0 Debug build (`com.stage11.c11.debug.<tag>`)
   cannot touch c11h's paths, defaults, sockets or hc sessions: it doesn't know their names.
2. **The old names live in one enum, `C11Identity.Legacy`**, read only by 266's migration and by the
   alias readers listed here. 266 gates every migration read on the release bundle id
   (`com.stage11.c11`), so a tagged or staging build never migrates.
3. **Hidden aliases only where they cost nothing:** the `c11h` CLI name, the `c11h-core` launcher name,
   `C11H_*` variables as fallbacks behind a central reader, the `c11h://` and `c11h-show://` schemes
   when typed or clicked inside the app.
4. **Wire names between machines stay as they are** (relay slot and method names, the relay credential
   label, the cbus envelope key). They are invisible, and keeping them is what lets a 2.0 app talk to a
   kit a c11h app installed (row 5).

## Running it

At the freeze, on a fresh checkout of `origin/main` that carries this branch's commits before the
generated one:

```bash
git submodule update --init ghostty vendor/bonsplit # the checkout must match main's gitlinks
python3 scripts/c11-2.0-rename.py --root .          # about 10 s; --check reruns it as a no-op test
git add -A -- . ':!ghostty' ':!vendor/bonsplit' ':!homebrew-c11'   # never stage a submodule pointer
git commit -m "C11H-265: generated by scripts/c11-2.0-rename.py (...)"
git cherry-pick <the hand-edit commits>              # applies cleanly on the regenerated tree
```

**Landing steps (right after the rename merges):** the codemod renames
`.github/workflows/c11h-shareable.yml` to `c11-shareable.yml`, whose guard names its own new path.
GitHub registers a pushed workflow path as active at once, and main's old guard then fails every
PR, so:

```bash
gh workflow enable c11-shareable.yml -R Stage-11-Agentics/c11h
gh workflow disable c11h-shareable.yml -R Stage-11-Agentics/c11h
gh run list -R Stage-11-Agentics/c11h --workflow c11-shareable.yml --branch main -L 1   # green
```

Until the freeze, no new workflow path is pushed (the Lead disabled `c11 shareable` after the first
push of this branch, 14:46).

`--report <file>` lists renames, per-rule counts, lines that contrasted c11 with c11h (a human
look), duplicate literals the rename created, and anything left.

**Any other open branch, after the rename lands, is one command:**

```bash
git fetch origin && python3 <(git show origin/main:scripts/c11-2.0-rename.py) --sync-branch origin/main
```

It merges the commit just before the rename into the branch, runs the exact codemod that made the
rename on the branch, commits, merges the generated rename commit (where a hunk differs, the
branch's side is the codemod's output on its own work, so it wins), then merges `origin/main`. What
can still conflict is only where the branch and the hand-edit commit touch the same lines. It merges
rather than rebases: a rebase would replay the branch's pre-rename commits onto renamed files.
Squash afterwards if the branch wants one commit. Proved on a scratch branch that edited a renamed
line, added a file naming `com.stage11.c11h` and edited a renamed script: no conflict, and its diff
against the renamed main was exactly its three changes.

**Writing new code on a pre-rename branch:** don't name an identifier with `C11H` followed by a
capital or at its end, or `c11h` as a word, unless the codemod should rename it. For a name that
must survive (an old path, a legacy constant), put `c11-2.0:legacy` on the line or wrap the block
in `c11-2.0:begin-keep` and `c11-2.0:end-keep`. Spell such a name `C11h` (as in `legacyC11h`) and no rule
touches it.

## Behaviour the rename does not change (noted for the Lead)

- **Telemetry stays off.** `TelemetrySettings.launchDecision` is off for every bundle, so 2.0 sends
  nothing although c11 1.8.1 could. The inherited gate would treat `com.stage11.c11` as production;
  turning telemetry back on is a decision for Atin, not a rename.
- **Skill install.** `SkillInstaller.installablePackageNames` becomes `["c11"]`: 2.0 installs the c11
  skill alone and leaves an installed `c11h` sidecar untouched. WS7 decides whether 2.0 returns to
  c11 1.x's MANIFEST list and how the sidecar folds in.
- **Socket variables in the CLI (C11H-282).** `C11_SOCKET`, `C11_SOCKET_PATH`, `CMUX_SOCKET_PATH` and
  `CMUX_SOCKET` are read in that order. A c11 socket is used; a c11h or cmux socket is skipped (their
  terminals export it, and terminals adopted from c11h still carry c11h's); any other path is refused
  when the CLI would connect, naming the variable and the path, where c11 1.8 used it and 2.0 had
  silently used its default instead. `--socket` takes any path. The app still binds only c11 names.
- **Shared default sockets.** `isForeignSharedDefaultSocketPath` is `!isOwnSocketPath`, as in c11h:
  a 2.0 staging build started from a c11 release terminal may take the release socket path, where
  c11 1.8.1 refused a fixed list. c11h's sockets are always refused. Restoring 1.8.1's list is a
  small change if the Lead wants it.

## Decisions

Decided by me (the Lead can overturn any with a word):

0. The rename is a codemod plus a hand-edit commit, and the codemod also carries a handful of exact one-line patches (`PATCHES`) where the token rule alone would make two names one: a Swift `Set` literal with a duplicate traps at launch (`PanelLinkFormat.acceptedSchemes`).
1. Internal Swift types and files lose the `H` too (`C11HRelay` → `C11Relay`): 52 types, no collision,
   and a public 2.0 tree with `C11H*` types reads as two products.
2. Defaults keys `c11h.*` become `c11.*`; 266 copies values across.
3. Build number 200, plain `2.0.0`, no `-hN` line.
4. Panel links register only `c11` with the OS; `c11h://` works only inside the app. A Mac keeps
   c11h.app after cutover (for going back), so registering both would let LaunchServices pick either.

For the Lead:

1. **Rename the hc and relay layer, or keep it c11h-named?** Recommended: **rename** (this map). Keeping
   `~/.local/share/c11h` and `c11h*` sessions is cheaper (old kits and live terminals need nothing), but a
   tagged 2.0 build would then share c11h's hc directory, which the brief rules out, and a 2.0 tag would
   collide with a c11h tag of the same slug. Cost of renaming: 266 must adopt `c11h*` sessions by name,
   and each linked machine is relinked once after cutover.
2. **Linked machines after cutover**: relink (above) and leave c11h-era remote terminals running under
   their old core, or have 266 adopt remote `c11h-s*` too? Recommended: relink now; remote adoption
   only if 266 finds it cheap.

## Appendix A: `C11H_*` variables

240 distinct names, 961 uses. The rule for all of them is `C11H_X` → `C11_X`, except the special
cases in the third table. No product name has an existing `C11_` twin, so none collides.

**Fallback mechanism (hand edit):** `mirrorC11CmuxEnv()` (`CLI/c11.swift`, `Sources/AppDelegate.swift`)
already runs first in the app and the CLI and fills `C11_X` from `CMUX_X`. One added branch fills
`C11_X` from `C11H_X` when only the old name is set, which covers every Swift reader at once. Shell
readers that meet live terminals get a one-line `${C11_X:-${C11H_X:-}}`. Live hc terminals keep the
environment they were started with, so the relay variables need the fallback. The relay protocol stays
at 2; nothing on the wire changes.

Product (26), each becomes `C11_<rest>`:

| Name | Set by c11h into | Fallback |
|---|---|---|
| `RELAY_BIN`, `RELAY_AUTH`, `RELAY_HC_SOCKET`, `RELAY_SESSION` | remote terminals and the relay shim | **yes** (Swift mirror plus shell sites in `Resources/bin/claude`, the relay shim) |
| `RELAY_PROTOCOL`, `RELAY_PICKUP`, `START_DIR` | the launch line (read and unset at once) | no; the launch line is generated per launch |
| `RELAY_CODEX_WRAPPER_REENTRY` | the relay shim, internal | no |
| `AGENT_NOTE_SENT`, `AGENT_NOTE_DISABLED` | the claude wrapper; `DISABLED` is user-set | `DISABLED` yes (one shell line) |
| `RELAY_CLAIM_MS`, `HOST_TRANSPORT_BUS`, `HC_FAULTS`, `LATENCY_LOG`, `HOST_END_RESUME_{INTERVAL_MS,SETTLE_MS,MAX_IN_FLIGHT}`, `MASS_SIGNAL_END_{WINDOW_MS,SETTLE_MS}`, `FORCE_MAIN_STALL`, `GRAPH_CHURN{,_PRINT,_LOG}`, `DEBUG_KEEP_SESSION_TWINS`, `TIP_PREVIEW`, `WHATS_DIFFERENT_SAMPLE` | read-only knobs | through the Swift mirror, free |

Tooling and local (214): renamed mechanically, no fallback, except `SHAREABLE_OVERRIDE` and
