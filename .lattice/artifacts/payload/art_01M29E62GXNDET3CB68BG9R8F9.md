## 3. Issues

**[MAJOR] Sources/Panels/BrowserPanel.swift:4278 — A declined prompt leaves the disposition stuck at `.prompting`**
`handleInsecureHTTPAlertResponse` records `.proceeded` only on `.alertSecondButtonReturn`. The `default:` branch (Cancel, and the unprompted synthetic Cancel) and `.alertFirstButtonReturn` (open externally) record nothing, so the panel's last disposition remains `.prompting(host:)` forever. `browser.url.get` (S3's designated poll surface) and the skill's own guidance then tell the agent "nothing loads until a human answers" after the human has already answered. The comment two lines above this branch says the point of the record is to keep that surface honest; it only does so for one of the three buttons. The unprompted path happens to be correct only because `presentInsecureHTTPAlert` overwrites with `.blocked` afterward.
**Fix:** Add a second case to `BrowserInsecureHTTPBlockReason` (e.g. `case declinedByOperator = "declined_by_operator"`, and optionally `openedExternally`), give it a `why` string in `browserInsecureHTTPBlockedError`, and record `.blocked(host:, reason: .declinedByOperator)` in the `default:` branch and a matching disposition in `.alertFirstButtonReturn`. Because the sheet completion fires asynchronously, also move `record(disposition: .prompting(host:))` to *before* `alert.beginSheetModal(for:)` so a synchronous test spy that answers immediately cannot have its answer overwritten by the later `.prompting` record; return the literal `.prompting(host: host)` from that branch. Add one host-target assertion: spy answers `.alertThirdButtonReturn`, then `panel.lastNavigationDisposition` is `.blocked(host:, reason: .declinedByOperator)`.

**[MINOR] Sources/Panels/BrowserPanel.swift:6499 — Consent lingers after a blocked cross-host redirect**
When an opted-in load to host A is 302'd to plain-http host B, `decidePolicyFor` blocks B and calls `decisionHandler(.cancel)`. WebKit then reports that as `WebKitErrorDomain` code 102, which `didFailProvisionalNavigation` early-returns on, so `didSettleNavigation` never fires and the consent for A is never released. `supersedeInsecureHTTPConsentIfNeeded` runs only from `navigate(to:)`, not from the delegate path. Net effect: if the operator cancels the B prompt (or there is no window), a later delegate-driven navigation to A (a link click, a JS `location` change) proceeds with no prompt, which is exactly the "silently apply to a later navigation to the same host" case the release logic's doc comment says it prevents. Bounded harm (A is the host the caller consented to), but it violates the stated scope.
**Fix:** Call `supersedeInsecureHTTPConsentIfNeeded(for: url)` at the top of `presentInsecureHTTPAlert`. A blocked navigation is by construction not covered by the current consent, so this clears a stale grant on every path that reaches the prompt, including the delegate one. Cover with a pure-helper assertion or a host-target test that seeds consent for A, presents the alert for B, and checks `hasPendingInsecureHTTPConsentForTesting(host: "A")` is false.

**[MINOR] Sources/Panels/BrowserPanel.swift:4211 — Unparsable-host branch misreports its reason**
A plain-http URL with no normalizable host returns `.blocked(host: url.absoluteString, reason: .noWindowToPrompt)`. The resulting error message says "no window available to prompt" and the hint says to pass `--allow-insecure-http`, but the flag is a no-op here because `consentToInsecureHTTP` guards on the same `normalizeHost` and bails. Low reach (`resolveNavigableURL` rarely yields such a URL) but the message actively misdirects.
**Fix:** Add `case unparsableHost = "unparsable_host"` to the reason enum with a `why` of "URL has no usable host" and return it here. If you take the MAJOR fix's enum extension, this is one more case in the same switch.

**[MINOR] skills/c11-browser/SKILL.md:46 vs :60 — The skill's default page-open path is still silent**
The existing "Default to a tab in the existing browser pane" rule tells agents to open pages with `c11 new-surface --type browser --url <url> --pane <ref>` (and `new-pane --type browser`). Those go through `SurfaceHandlers.swift:423` / `PaneHandlers.swift:246-260`, which take no `allow_insecure_http` and report no disposition, so an agent following the skill's own default hits the exact silent path this ticket closes. The new section teaches the flag for `open`/`goto` only. In-scope-by-letter (the ticket names "a flag on the open verb"), but the skill now contradicts itself for the LAN/tailnet case.
**Fix:** Cheapest: one sentence in the new section stating that `new-surface --url` / `new-pane --type browser --url` do not accept the flag or report the outcome, so for non-loopback plain-http, create the surface without a URL and then `goto <url> --allow-insecure-http`. Better, as a follow-up ticket: plumb `allow_insecure_http` and the `insecure_http` payload fragment into `surface.new` and `pane.new` the same way `open_split` does.

**[MINOR] skills/c11-browser/SKILL.md:66 — "same-host redirects" overpromises for client-side redirects**
The consent survives HTTP redirect hops because they occur before `didFinish`. A dev server that serves `/` and then redirects via JS or `<meta http-equiv="refresh">` (common for SPA login gates) fires `didFinish` first, which releases the consent, and the follow-on navigation prompts or blocks again. The skill's "`/` → `/login` works" is true for a 302 and false for a client-side redirect to the same path.
**Fix:** One clause: "HTTP redirects are covered; a page that redirects itself with JS after loading starts a new navigation and needs consent again (check `get url --json`, re-issue with the flag)."
