# Layout: where new work goes

Print this page with `c11 guide layout`. Panels, areas and workspaces; the two-area ceiling; size checks; browser placement; windows; and the operator's visible workspace. A link to `<page>.md` names another page: `c11 guide <page>`.

**Where new work goes:** a new **panel** in an existing area for nearly everything you open (a sub-agent, a log tail, a browser for validation, a doc); a new **area** only while the workspace has a single area and the work wants its own spatial slot; a new **workspace** only when the operator asks for one or names a *different project*. A new task, mission or fleet inside the same project is not a reason for a new workspace. When the operator asks for a "surface", "panel", "instance" or "agent", put it in your current workspace. Default to one workspace per project unless the operator's setup says otherwise. **Wanting agents isolated from each other is not a reason for a new workspace** — same-workspace agents are already separate processes with separate context; blindness between agents comes from their prompts, never from topology (see [references/orchestration.md](orchestration.md#isolation-is-a-prompt-rule-not-a-topology-rule)).

**A workspace made for an agent is born with it.** `c11 launch-agent --type <kind> --new-workspace --cwd <dir> --json` creates the workspace with the agent as its one panel, rooted at `<dir>` (the workspace root comes from `--cwd`). Then name it by the `workspace_ref` the JSON returns: `c11 rename-workspace --workspace <workspace_ref> "<title>"`; without `--workspace` it renames the workspace you are in. `c11 new-workspace` followed by a launch into it leaves an empty shell panel beside the agent. `--new-workspace` takes neither `--split` nor `--on`.

**Two areas is the ceiling you reach on your own.** Count first: `c11 list-areas`. One area: you may split once, to make a second. Two or more: add panels (`new-panel --area`, `launch-agent --area`, `browser open --area`, `markdown open --area`); a third area needs the operator's word or a layout you proposed up front ([orchestration](orchestration.md#layout-philosophy)). Every area you add halves what the operator can read, while a panel costs no screen at all. `new-panel` and `launch-agent` never split; `new-split` and `new-area` always do. Without `--area`, `launch-agent` lands in the workspace's *focused* area, wherever the operator left it, so pass your own area from `c11 identify --json`. **Group by kind:** what the operator reads (browsers, markdown) shares one view area; what runs (agents, shells, log tails) shares one terminal area. A second browser joins the first browser's area; a second sub-agent joins the first sub-agent's. Observed failure (2026-11-06): an agent opened a browser in a new area, then a sub-agent in another, and the operator's workspace became slivers. The browser was a fair first split; the sub-agent should have been `launch-agent --area <your area>`.

**c11 checks the size for you; read the room anyway.** A split whose halves would fall below 80×20 cells for an agent, 40×10 for a plain terminal, or 320×240 pt for a browser or markdown panel is refused (`pane_too_small`; the message names the remedy) or flipped to the axis that fits, and `size_outcome` / `size_warning` in the result say which. Those are floors, not comfort: an agent reads well at 120×30. Before a split, read the area's `pixel_rect` in `c11 tree --json`; when either half would land within 15% of its minimum, add a panel instead. `--allow-undersized` is for an operator who asked for exactly that split, never a workaround.

**Place browsers by anchor, never by focus.** `browser open`, `open-split`, and `new` anchor on the caller (`$C11_PANEL_ID`) unless `--panel` or `--area` is given. The first open splits beside the anchor when space permits; later opens join its browser area. A cross-workspace `--workspace` open adds a panel to an existing area without splitting. `--area <ref>` adds there without splitting, and is how a browser joins a markdown panel's area or any other view area that already exists. `open --panel <browser>` still navigates that browser in place; `--panel <terminal>` places beside it.

- **Windows have names, themes and places.** `c11 display list` and `c11 list-windows --json` say which display every window is on, in global points with the origin at the main display's top-left (y down). A window name is a `--window` ref. `c11 window move` places a window on a display without raising it; move windows only when the operator asks. Details: [Windows and displays](api.md#windows-and-displays).
- **Agents never change the operator's visible workspace.** Socket selection, workspace cycling and cross-workspace browser focus return `workspace_switch_blocked`; there is no setting or override. Raise a flag when the operator needs to look. Background panels support send, browser eval/click/snapshot, creation, agent launch and metadata. `focus-panel` and `focus-area` change focus inside their target workspace without selecting it. Hidden browsers can pause timers/video; ask the operator to view them when visible playback is essential.
