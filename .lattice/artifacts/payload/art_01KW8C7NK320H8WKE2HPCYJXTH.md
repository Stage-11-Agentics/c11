# Plan Review: C11-151 — opencode exact-session resume via plugin rail

## 1. Verdict

**PASS** — The plan is complete, technically sound, and well-aligned with the task. The architecture understanding is verified against the live codebase, the load-bearing base62 fix is correctly identified, and decomposition is clean. One major *validation-step* gap (plugin reinstall/activation before the live gate) and a few minor refinements are noted below; none invalidate the design, but the plugin-install item must be addressed before the live acceptance gate is run or it will misdiagnose.

## 2. Summary

I reviewed the C11-151 plan against the actual c11 source: the `ConversationStrategy` protocol and inputs (`Sources/Conversation/Strategy.swift`), `ClaudeCodeStrategy` (the reference being mirrored), the placeholder `OpencodeStrategy`, `StrategyRegistry.v1`, the `AgentManifest` opencode entry, `SurfaceMetadataStore`/`WorkspaceMetadataKeys`, the restore dispatch precedence in `Workspace.swift`, the `feat/opencode-resume` WIP branch, the `c11-notify.js` plugin, and `SkillInstaller`. The plan's central claims check out: the Crockford-vs-base62 grammar bug is real and load-bearing, the two-rail architecture description is accurate, and the restore precedence (ConversationStrategy path is the live default; `AgentManifest.resume` fires only under the kill switch) is correct. The key concern is that the live acceptance test silently depends on the *installed* plugin copy at `~/.config/opencode/plugins/c11-notify.js`, which the plan's validation section never refreshes or verifies.

## 3. Issues

**[MAJOR] §3 + §8 (Validation) — Live gate depends on the installed plugin copy, which the plan never refreshes**
The live acceptance criterion ("live opencode quit+relaunch resumes the exact `ses_` session") requires `~/.config/opencode/plugins/c11-notify.js` — the copy opencode actually loads — to carry the new `session.created` handler. opencode loads plugins from `~/.config/opencode/plugins/` (`SkillInstaller.swift:51`), and `SkillInstaller.installPlugins` copies them there from the repo's `skills/opencode-plugins/`. The plan's claim in Verified facts ("opencode-plugins is **not** in `skills/MANIFEST.json` `installable` → editing `c11-notify.js` needs **no** `sync-installed-skills.sh` run") is *true but misleading* — it's the right negative for the wrong reason. `sync-installed-skills.sh` is irrelevant here, but a **different** install refresh (via `SkillInstaller`, the Agent Skills settings flow, or whatever the tagged build runs on launch) is still required to get the edited handler into the live plugin path. If the operator already has an older `c11-notify.js` installed, the tagged build's opencode loads the stale copy, no `session.created` push fires, no `ConversationRef` is captured, and the live test fails for an *install* reason — not a code reason — burning a confusing debug cycle right at the `pr_open` gate.
**Recommendation:** Add an explicit validation step before the quit+relaunch: (re)install/refresh the opencode plugin from the tagged bundle and verify `~/.config/opencode/plugins/c11-notify.js` contains the `session.created` handler (e.g. `grep session.created ~/.config/opencode/plugins/c11-notify.js`). Confirm whether the tagged build auto-overwrites the installed plugin on launch; if it does not, document the manual reinstall command. Treat "plugin handler is live in `~/.config/opencode/plugins/`" as a precondition of the live gate, not an assumption.

**[MINOR] §7 (Tests) — Parity test lives in the host scheme, not the local `c11-logic` loop**
The plan validates locally with `c11-logic` (correct, per the testing policy) and asserts "confirm `AgentManifestTests` parity test stays green." But `testConversationStrategyPresenceParity` lives in `c11Tests/AgentManifestTests.swift` — the host-required `c11-unit` target — as do `ConversationStrategyTests` and `WorkspaceConversationResumeTests`. None of those run under the `c11-logic` scheme the plan uses locally, so the parity assertion is effectively **CI-verified only**, not part of the local loop the plan leans on. Since opencode already has `hasConversationStrategy: true` and is already in `StrategyRegistry.v1`, parity is in fact unchanged — but the plan should state that this check is deferred to CI rather than implying local verification.
**Recommendation:** Note explicitly that the parity test is host-scheme/CI-verified. New `OpencodeStrategy.resume`/`capture` tests can live in `c11LogicTests` (the `c11` target it depends on exports the strategy types, so they compile/run there) — that's fine — but call out that this splits opencode strategy coverage across two targets from the existing `ConversationStrategyTests`. Either co-locate or accept the split with a one-line rationale.

**[MINOR] §5 / Risks — SQLite linkage reasoning is muddled (low actual risk)**
The risk note ("`ClaudeCodeScraper` has no SQLite but the build links libsqlite3 implicitly via the SDK — verify compile") draws a false comparison: `ClaudeCodeScraper` is filesystem/`stat`-based, so it tells you nothing about SQLite linkage. The real basis for confidence is that `import SQLite3` resolves against the macOS SDK system module and auto-links `libsqlite3.tbd` — which the existing WIP `OpencodeScraper` already does. Risk is genuinely low; the muddled justification is the only issue.
**Recommendation:** Drop the `ClaudeCodeScraper` comparison; rely on the actual `c11-logic` compile in item 8 as the proof, and keep `import SQLite3` as the WIP already has it.

**[MINOR / WATCH] §4 (resume) — Confirm the exact interactive opencode flag combo at live test**
The plan types `opencode --dangerously-skip-permissions -s <id>` for the interactive (TUI) resume, distinct from the manifest's factory `resume: .fixed("opencode run --dangerously-skip-permissions\n")`. Restore precedence is correct (verified: `Workspace.scheduleAgentRestart` uses `ConversationStrategyRegistry.v1` as the live default; the legacy `AgentRestartRegistry`/`AgentManifest.resume` path only fires under `CMUX_DISABLE_CONVERSATION_STORE=1`), so there is no double-launch conflict. The open question is purely whether `--dangerously-skip-permissions` is a valid flag for the *interactive* `opencode -s` invocation (the manifest pairs it only with `opencode run`).
**Recommendation:** During the live test, eyeball that the restored surface's typed command actually re-attaches and that `--dangerously-skip-permissions -s <id>` is accepted by the TUI (not just `opencode run`). If the flag is `run`-only, fall back to bare `opencode -s <id>`.
