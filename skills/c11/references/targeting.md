# Targeting, refs and CLI rules

Print this page with `c11 guide targeting`. How to name a target, which refs survive a restart, how panel writes, reads and close commands resolve, and how to read panel state. A link to `<page>.md` names another page: `c11 guide <page>`.

## Ask this build

**Ask this build:** `c11 guide` (alias `c11 --skill`) prints the skill shipped in
the CLI's app bundle, including its build identity and skill version, with no
socket required. `c11 guide api` prints a bundled reference page. An installed
skill copy can be older than `c11 guide`; printing the guide does not update it.
`c11 capabilities --json` reports the connected server's methods and enabled
versioned features, both CLI/server identities, and `sha_match` (null when a
commit stamp is unavailable). Use that server feature list to check support;
the PATH CLI can belong to a different build.

**Read the fleet:** `c11 fleet --json` returns every live agent terminal across
all windows and workspaces in one read-only request. Plain `c11 fleet` prints a
short table. Check feature `fleet` (version 2 for filters and `--since`, 3 for `stalled`, `context` and `restore`); the versioned schema, source
semantics and explicit nulls are in [the API reference](api.md#fleet).
Each agent row says why it is stuck (`blocked`: a usage limit with its reset
time, an API error, a permission prompt, a question, Claude's resume dialog),
what its prompt shows (`input`), which login it runs on (`account`), its last
message (`last_message`), how its last turn ended (`last_turn_stop`), whether
it has gone quiet (`stalled`: no output while working, or a turn that ended
announcing work and nothing followed), its prompt size against its model's
window (`context`) and its restore outcome after a relaunch (`restore`), so a
watcher needs no `read-screen`. Unknown values are null, never guessed. Narrow
it server-side (`--workspace`, `--group`, `--lifecycle`, `--flagged`,
`--blocked`, `--stalled`, `--parent`), and for a heartbeat pass the last
`fleet_seq` as `--since`, with the same filters, to get only the agents that
changed; drop the ids in `removed_panel_ids`, and replace your copy when
`full` is true.

**Wake on a dead seat instead of polling:** follow
`c11 events tail -f --filter agent` (add `--filter workspace=<uuid>` for one
ship). It streams `agent.blocked`, `agent.unblocked`, `agent.stalled` and
`agent.unstalled` from the same verdicts fleet shows, and
`agent.restore_needs_operator` for each seat a relaunch left for the operator, then read
`c11 fleet --json --since <fleet_seq>` for the details. Keep a heartbeat fleet
read (every 30 minutes is enough): it keeps the screen sweep on, which is how
c11 sees resume dialogs and limit menus. [Events](events.md#agent-edges).

`C11_SHELL_INTEGRATION=1` means you're inside c11 — prefer native workflows (splits, the embedded browser, `c11 set-metadata`) over Chrome MCP or plain `open`. Other env vars available to child processes: `C11_WORKSPACE_ID`, `C11_PANEL_ID`, `C11_SOCKET_PATH`, `C11_PANEL_NUM`. The spawn path may also pre-seed `C11_AGENT_TYPE`, `C11_AGENT_MODEL`, `C11_AGENT_TASK`.

`open` on PATH inside a panel is the bundled `Resources/bin/open` shim. In the shipped layout it falls back to system `open`, and the destination depends on the OS handler for that URL. Use `c11 browser open <url>` for a c11 browser panel. When a specific external browser is required, use `/usr/bin/open -a <browser> <url>`.

## Refs

Refs accept UUIDs, short refs, or indexes: `workspace:1`, `area:2`, `panel:3`. **A bare number from the operator is a panel ref.** Panels display `N: title` by default (the "Show Panel Numbers in Panel Titles" setting; if the operator turned it off, panels show titles only), where N is its `panel:N` ordinal — so "send that to 292" means target `panel:292` (with its `--workspace`). Always write the `panel:N` form; a bare integer in a CLI flag is a positional index, a different thing. Your own N is `$C11_PANEL_NUM`. Each sidebar workspace card shows its `workspace:N` number as `WS N` in the top-right corner (the "Show Workspace Numbers in Sidebar" setting), so "workspace 10" or "the one in 10" means `workspace:10`, not the tenth card. A workspace nobody has named is titled `Workspace N` (localized) with that same N. `--pane` (tmux-compat) targets an area; `--panel` targets a panel.

**Panel numbers survive restarts; other short refs last only for the current c11 process.** A panel keeps its `panel:N` (and `$C11_PANEL_NUM`) across a restart, and a closed panel's number is never given to another panel. `close-panel --expect-title <text>` closes only when the target's current title exactly matches `<text>`; on mismatch it leaves the panel open. Its success line keeps the `OK <panel> <workspace>` prefix, then appends the UUID if `--id-format` did not already show it and the JSON-quoted title; JSON uses `panel_title`. `area:N`, `workspace:N`, and `window:N` ordinals start over at launch; such a ref saved before a restart can name a different object afterward. A `--window`, `--workspace`, `--area` or `--panel` value that resolves to nothing (a ref from an earlier launch, an unknown UUID, index or name) fails with `not_found` on every command and changes nothing; only an omitted flag takes the command's default. Keep using short refs for live targets. To store a reference across restarts, prefer the UUID from `c11 --id-format both tree --json` or `$C11_PANEL_ID`, and use that UUID. `$C11_WORKSPACE_ID` likewise identifies the workspace; do not store its ordinal across a restart. It names the workspace your shell started in. When your panel moves to another workspace, the CLI looks up where `$C11_PANEL_ID` lives now, so commands that default to your workspace follow the panel; a script reading the variable itself should run `c11 --id-format both identify --json` for the live one.

## Writes, reads, options and closes

> **Pass `--panel` explicitly on panel-scoped writes.** Every panel exports `$C11_PANEL_ID` (inherited by subprocesses), so `--panel "$C11_PANEL_ID"` targets you correctly. A panel-scoped write with a **missing or empty** ref is **rejected** with a clear error (`missing_ref` / `empty_ref`) rather than falling back to the operator-focused panel, so an omitted or empty flag fails loudly instead of stomping a peer agent's panel. You must therefore still pass a valid ref: if `$C11_PANEL_ID` reads empty, capture your refs once from `c11 identify --json` and pass the literal `panel:<n>`. Applies to every panel write (`set-metadata`, `set-agent`, `set-title`, `set-description`, `set-panel-icon`, `set-panel-color`, `rename-panel`, `clear-metadata`, `trigger-flash`). Sidebar metadata commands are workspace-scoped: `--workspace` is explicit, and `$C11_WORKSPACE_ID` supplies the caller's workspace inside c11. Pass `--workspace` from a bare shell or cron. Every sidebar command (`set-status`, `set-progress`, `log`, `clear-status`, `clear-progress`, `clear-log`, `list-status`, `list-log`, `sidebar-state`) fails when neither target is available; global `--window` alone is not a workspace target, and these commands never use the operator's selected workspace. On sidebar writes (`set-status`, `set-progress`, `log`), `--panel <ref>` names a panel, mirrors the status onto it, and needs a workspace to resolve in; a bare number is rejected as ambiguous. Verify the first write with `c11 get-titlebar-state --panel <panel>` against the panel marked `◀ here` in `c11 tree --no-layout`.

> **Panel reads validate explicit targets before defaulting.** On a panel-targeted read, `--panel` (or the hidden aliases `--surface` / `--tab`) needs a value. A flag with no value reports `--panel requires a value`; an explicitly empty value (including `--panel=` with nothing after it) is rejected as `empty_ref` before the command can fall back to the caller's panel. A stale explicit target on `get-metadata`, `get-titlebar-state`, `read-screen`, `read-selection`, or `input-state` returns `not_found` before reading any panel; it never reads the focused panel instead. Omitting the flag keeps that command's documented default. This covers `identify`, `read-screen`, `capture-pane`, `pipe-pane`, `read-selection`, `input-state`, `get-metadata`, `get-titlebar-state`, `family`, `panel-color get`, markdown reads, browser reads including `browser eval`, URL and webview reads, conversation reads, and `mailbox recv` / `mailbox inbox-dir`.

> **CLI options fail closed.** c11 rejects an unrecognized flag before socket discovery and sends nothing. `--json` and `--id-format <fmt>` work after any command's own options, the same as `c11 --json <command>`, and every option that takes a value also accepts `--name=value`. Text stays text: after `--` on commands that take literal text, in trailing command lines (`respawn-pane`, `pipe-pane`, `set-hook`, and `ssh <dest> -- <cmd>`; a bare `--word` after the ssh host is refused), in browser `type`/`fill` words, and in tmux words after the first non-option. On other commands a flag after `--` is still rejected. Commands that read no positional word, or a fixed number of them, reject one more before contacting the app: `close-panel panel:268` fails with `Did you mean --panel panel:268?` and sends nothing. Commands that take free text or a list of words accept extra words, and a few accept a word their parser ignores (`new-area right` still splits by `--direction`, default right). `claude-teams` passes its remaining options to Claude Code.

> **Close commands need an explicit target.** `close-panel --panel <ref>`, `close-workspace --workspace <ref>`, `close-window --window <ref>`, and the close actions of `panel-action` / `workspace-action` never fall back to your panel or the focused one. `close-panel --expect-title <text>` compares the live panel title exactly before closing and refuses without changing anything on mismatch. To close yourself, say so: `--panel self` (or `--workspace self`, `--window self`) means the `C11_PANEL_ID` / `C11_WORKSPACE_ID` in your environment and fails when it is unset. A subagent inherits its parent's `C11_PANEL_ID`, so `--panel self` from a subagent closes the parent agent; pass the ref of the panel you mean. The tmux shim's `kill-pane` and `kill-window` require `-t`.

## Enumerating and reading panel state

- **There is no `c11 list`.** Enumeration is scoped: `c11 tree --all` (every window — the one to reach for when asking "is any agent working on X?"), `c11 tree --all --json` to script against, or `list-workspaces` / `list-areas` / `list-area-panels`. `c11 list` is *not* a command — it errors and prints usage, so `c11 list | grep <x>` greps the **error text**, comes back empty, and reads exactly like a clean "nothing found." Don't let a command that never ran become a confident answer: if an enumeration is empty and it matters, run it bare and confirm you got a tree.
- **Per-panel `prompt_cache` says whether an agent's next message re-caches its context.** Every panel in `c11 tree --json` / `panel.list` carries `prompt_cache`: `null` without cache evidence, `{state: unknown}` when a reporter cannot tell, else `{state: warm|cold, basis: ttl|estimate, lifetime_seconds, requested_at, cold_at, prompt_tokens, source: transcript|report|statusline, misses}`. Prefer a warm agent, or message one before its `cold_at`, when the choice is free. Plugins, extensions and custom kinds report a request's cache use with `c11 rpc agent.prompt_cache.report`; the operator can paste a statusline snippet that reports Claude Code's exact cache (c11 never writes it). Details: [references/api.md](api.md#prompt-cache-reports).
- **Per-panel `last_seen_at` says when the operator last looked at a panel.** Every panel in `c11 tree --json` / `panel.list` carries `last_seen_at` (ISO-8601, second precision, `null` = never seen) and `being_seen`. A panel is seen while it is the selected panel of the focused area in the selected workspace of the key c11 window, with c11 frontmost, the window on the active Space and visible, and the screen unlocked. Because it follows what is on screen, a socket focus change while c11 is in the background stamps nothing; while c11 is frontmost it stamps the panel that left and marks the new one `being_seen`. Details: [references/api.md](api.md).
- **`c11 history --json --limit 50` reads completed seen visits and explicit operator-jump endpoints.** UUID targets survive restore; `history back` / `history forward` may focus within the selected workspace, while cross-workspace navigation returns `workspace_switch_blocked`. Live titles are returned but never persisted in history. An ordinary open visit is not listed; explicit jump arrivals are. Schema, privacy and key bindings: [references/api.md](api.md#focus-history).
- **Creation lineage** is visible through `c11 family [--panel <ref>] [--json]` and `c11 tree --json`. A panel node's `parent_panel_id` is the creator UUID or `null`, and its `origin` says who made it: `operator` (an operator click, shortcut, menu or sidebar action), `panel` (made from its parent panel), `app` (c11 itself; `origin_detail` is `launch` (the workspace c11 opens when it starts with nothing to restore), `restore` or `chaos`), `external` (a socket or CLI call with no caller panel: cron, a LaunchAgent, a bare shell) or `unknown` (recorded before origins existed, or the creator was lost). A null parent alone never means the operator made it. `get-metadata` also shows the parent's current ref and last known title, and the origin as `panel_origin` / `panel_origin_detail`, as read-only projections. Closed ancestors remain in a family's output while a live descendant depends on them. `c11 family` includes each node's type, title, live/closed state, delegate status, and workspace; a future HTML family view may read `c11 --id-format both family --json` for stable UUIDs.
- **`c11 rpc <method> [json]` is a local raw socket call** for methods without a friendly command. Prefer the command when one exists; remote calls over `c11 ssh` remain unavailable.
- **Socket/CLI commands never steal macOS focus**, and telemetry commands run off-main — don't expect a `send` to raise a window. The one exception is the explicit `c11 focus-window --window <id>` command, which raises and activates its target window (it never changes which workspace a window shows). Global `c11 --window <id>` scopes the command without raising that window. A panel or workspace outside the scoped window is an error.
