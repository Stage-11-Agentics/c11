# Code Review: C11-209 — browser JS await wedge

## 1. Verdict

**FAIL (implementation-level)**

The plan is sound and the production code is correct as far as I can verify by reading it against the live sources. The blocker is the test target choice: one new test crashes the bare xctest runner in CI, and that crash cascades into ~50 spurious failures, so the `build` gate (PR #433, run 34661457913) is red. The plan's own resolution R5 already prescribes the fix (move the WKWebView-constructing tests to `c11Tests`). One rework cycle; no plan change needed.

## 2. Summary

Reviewed the full diff (nine files, +1,051/−53) against the plan and the R1–R9 resolutions, and cross-checked every claim that depends on code outside the diff: `notifyOnMain`, the three `.browserDownloadEventDidArrive` post sites, `TerminalController`'s own download observer, `v2BrowserWithPanel`, `socketWorkerV2Methods` (no `browser.*` entry, so every browser handler is main-bound as the plan states), the hibernate / reattach / process-termination web-view replacement paths, `performNavigation` → `browserLoadRequest` → `load`/`loadFileURL`, the floating-popup path, and the pbxproj target membership (new file is in `c11LogicTests`, phase `37DDE3B0A6A70E75A7B2BEDF`, as planned). CI, however, shows `testLoadHTMLStringMarksLoadIssued` trapping inside `WKWebView.loadHTMLString` with no host app, exactly the R5 risk, and `origin/main` at the same base is green, so the failure is introduced by this branch.

## 3. Issues

**[CRITICAL] c11Tests/BrowserAwaitPolicyTests.swift:68 (and GhosttyTabs.xcodeproj/project.pbxproj:1732) — `loadHTMLString` on a `CmuxWebView` traps in the host-less `c11LogicTests` runner; CI `build` gate is red**
CI log (job 103464648988) shows `Program crashed: Signal 5: System trap` with frame 0 at `CmuxWebView.loadHTMLString(_:baseURL:)` (`Sources/Panels/CmuxWebView.swift:118`, the `super` call) called from `testLoadHTMLStringMarksLoadIssued`. xcodebuild then restarts the runner ("Restarting after unexpected exit, crash, or test timeout") and in the fresh process every workspace/TabManager-constructing suite dies with `GhosttyTerminalView.swift:1214: Fatal error: Unexpectedly found nil` and `bundleProxyForCurrentProcess is nil` (NewWorkspaceTitleTests, PanelIdentityRestoreTests, WorkspaceLayoutExecutorAcceptanceTests, TabManagerSessionSnapshotTests, and ~10 more suites). Those are the same tests `CLAUDE.md` documents as host-sensitive, and they pass on `origin/main` run 34655317465 at the identical base SHA, so the cascade is caused by this branch. Note the interesting detail that `load(URLRequest(about:blank))` and `reload()` survived in the same process while `loadHTMLString` did not; the boundary is per-API, so nothing that asks WebKit to actually load belongs in the logic target.
**Fix:** Split the file per R5. Keep in `c11LogicTests`: the three clamp tests, the five pump tests (all passed once the runner restarted), `testFreshWebViewHasNotIssuedALoad`, `testPlainWKWebViewIsTreatedAsLoaded`, and the `markLoadIssued()` test, none of which trigger a web-process launch. Move `testLoadRequestMarksLoadIssued`, `testLoadHTMLStringMarksLoadIssued`, and `testReloadMarksLoadIssued` into a new `c11Tests`-target file (e.g. `c11Tests/CmuxWebViewLoadTrackingTests.swift`, added to phase `F1000005A1B2C3D4E5F60718`). Verify by parsing the new run's log for `** TEST SUCCEEDED **` under "Logic tests (gate)" with no "Restarting after unexpected exit" line; a green checkmark alone does not prove the cascade is gone.

**[MINOR] Sources/SocketHandlers/BrowserQueryHandlers.swift:935 — a live-delivered download event is now returned twice across consecutive `browser.download.wait` calls**
`TerminalController.init` (`Sources/TerminalController.swift:374`) also observes `.browserDownloadEventDidArrive` with `queue: .main` and appends the event to `v2BrowserDownloadEventsBySurface` via `Task { @MainActor }`. That append cannot run inside the pump but does run as soon as the drain finishes. So the sequence is: call 1 receives `ready_to_save` live via the new `queue: nil` observer and returns it; call 2 finds the same event at the head of the queue and returns it again. Before this change the live observer could never fire, so the queue was the only delivery route and there was no duplicate. This is a pre-existing design gap that the fix makes newly observable; it will mislead any agent that polls `download wait` in a loop.
**Fix:** Make the queue the single source of truth. Switch `TerminalController`'s observer to `queue: nil` and append under `MainActor.assumeIsolated` (every post site is a WebKit delegate on main, same argument the diff already makes), then have the waiter's live path pop the matching event from `v2BrowserDownloadEventsBySurface[surfaceId]` before returning, or simply have the waiter's observer do nothing but `finish(())` and re-read the queue head after the await. Either way, add the corresponding V6 row: two consecutive `download wait` calls after one download return one event, not two.

**[MINOR] skills/c11-browser/SKILL.md:96 — skill overclaims the error code**
The new paragraph says every JS command (`eval`, `wait`, `snapshot`, `get text`, `click`, …) "returns `no_document`". Only `browser.eval` and `browser.wait` carry the `no_document` code and the `current_url` / `lifecycle_state` data (`v2BrowserNoDocumentResultIfNeeded` is wired into exactly those two, as the plan scoped). Every other JS path hits the `v2RunJavaScript` choke point and surfaces as `js_error` with the generic "navigate first" message, and the "navigation was requested but withheld" distinction is lost there. An agent branching on the code will miss it for `snapshot`/`click`/`get text`.
**Fix:** Either (a) wire the pre-check into `v2BrowserSelectorAction` and the other `v2BrowserWithPanel`-based JS handlers (one `if let refusal = … { return refusal }` each), or (b) reword the skill to say the *message* is immediate and only `eval`/`wait` return the `no_document` code. (a) is small and makes the skill true; (b) is the minimum.

## 4. Positive Observations

- **The diagnosis was narrowed honestly before anything was built.** The ticket's headline ("EVERY browser JS eval … is guaranteed to fail") was disproven with a real-`WKWebView` harness, the `deadport`/`hanging` rows showed `url == nil` is the wrong predicate, and the doc's "Correction" section says so plainly instead of quietly shipping a fix for the wrong bug. The `hasIssuedLoad` predicate falls straight out of that measurement.
- **One guard at the choke point.** Placing the fail-fast in `v2RunJavaScript` covers all ~35 JS call sites at once, including the dead-but-still-compiled `v2BrowserEnsureInitScriptsApplied`, and the `?? true` cast rule means the guard can only ever avoid a wedge, never invent a failure on a view the app did not create.
- **The pump change is exactly as small as it needs to be.** Lock-guarded `resolved`/`result` plus `CFRunLoopWakeUp` on off-main resolution; nothing else about the C11-165 slicing contract moved. The corrected comment is now a precise statement of what the pump can and cannot deliver, names the busy-spin cost, and records the `c11 ping` vacuity so the next validator does not repeat R1.
- **The tests reconstruct the real frame.** `inMainQueueDrain` uses `DispatchQueue.main.asyncAndWait` from a worker queue, matching the production `sample(1)` stack, and `testMainQueueDeliveryCannotResolveThePump` asserts the *negative* case rather than only the happy path. Those five tests passed in the restarted runner, so once the WebKit tests move the file will be green.
- **`browser.download.wait` was rewritten with the R3 discipline, not around it.** Every mutation of `finished`/`source`/`timeoutWorkItem` is on `watchQueue` with a `dispatchPrecondition` to prove it; the fd is closed from the cancel handler and the teardown `watchQueue.sync` cancels on every exit path, so a deadline unwind can no longer race a live source. I looked for a main-hop inside anything that runs on `watchQueue` (the sync-from-main deadlock shape) and found none. The `ready_to_save` post was correctly moved out of the `DispatchQueue.main.async` block on the *posting* side, which the plan had not anticipated and which the notification route needed.
- **Clamp semantics are transparent to the caller.** `requested_timeout_ms` is echoed only when clamping actually happened, in all three error payloads.
- **The writeup lands with the code**, with a "Status after C11-209" section that separates what shipped, what was deliberately not done (the off-main handler move), and what is still unexplained (the 25-minute stall), rather than implying closure.
