# Experiments: herdr-core 0.1.14 on the laptop and a Prime box

Run 2026-10-30, 03:10 to 03:33 PDT, by Cairn for `EXPLORATION.md`. Binary: the `macos-aarch64` release tarball from `releases.herdr.dev/core/0.1.14/` (tarball SHA-256 `ca524329…7970`, matching `manifest.json`; the binary inside reports `hc 0.1.14`, unsigned, ad hoc identifier `herdr_core-7c4b86435c74e04c`). Machine: the laptop (M4 Max, macOS 26.6.2), one-minute load 7 to 10 throughout, shared with Atin's agent fleet. Every core ran in an isolated session (`HC_SESSION=c11x`, XDG state and config under the session scratchpad, sockets in `/tmp/c11hcx`), started from this c11 terminal. Every core, holder, probe program and Prime box was stopped and deleted at the end; `pgrep` found nothing left and `prime sandbox list` was empty.

Harness: `probe/hcx.py` (framed protocol: attach, first paint, queries, flood, throughput, latency, raw calls), `probe/qprobe.py` (the query script a program runs), `probe/directlat.py` (the no-hc baseline), `probe/cc7501.py`, `probe/evwatch.py`, `probe/attachwatch.py`, `probe/fed-prime.sh` (the third federation run; the earlier two had a CLI mistake, see 18), `probe/respprobe.c` (the TCC probe from the Step 0 spike). Latency numbers come from Python harnesses on both ends, so compare rows with each other, not with the Step 0 Rust `latbench`.

| 15 | **TCC responsibility** (`respprobe`, the private `responsibility_get_pid_responsible_for_pid`) | The core and the holder started from this c11 terminal, the core the holder restarted after the kill, a program inside an hc terminal, and that program's zsh child all report responsible pid 86606, `/Applications/c11.app/Contents/MacOS/c11`. | 17 | **Claude Code 2.1.314 inside an hc terminal** (real binary, c11 env blanked, a scratch cwd) | Within 1.5 s: `reported: true`, `status: {app: claude-code, state: idle}`, title `Claude Code`. Codex 0.165.0 has no 7501 strings. c11's Ghostty fork has no 7501 parser, so Claude never reports inside c11 today. Killed after 6 s; no prompt was sent. | V |
| 18 | **Federation to a Prime box** (`buildpack-deps:bookworm-scm`, x86_64, 2 vCPU, `prime --plain sandbox ssh <id> --` as the `--via` command) | `hc machine add --install` took 25 to 27 s (it downloaded the Linux x86_64 release on the laptop, streamed it through the gateway, started the remote core); `connecting` to `connected` in about 6 s. Remote `terminal.run` via the API: `box/t1`, `box/t2` live and merged into the local list and event stream. Attach through both cores: first paint 302 bytes; echo RTT p50 167, p99 193 ms through Prime's gateway (the build host over the tailnet would be a different number). `hc exec --on box` and `hc file read --on box` worked. Killing the ssh child and its wrapper: `connecting` 3 s later, `connected` 6 s later; the attached stream stayed open (no CLOSE); events showed `created box/t2` again plus a local `missed`. Stopping and restarting the local core: the machine reconnected and the remote bash (pid 792) was still live. The remote core logged `no systemd user manager here: the core ends with whatever started it` and still survived both drops. CLI gotcha found on the way: `hc run … <program> --json` hands `--json` to the program. | V |

Still not run: IME, bell, kitty graphics, the 4 MiB flood repaint with the core's memory under a flood, a real remote machine inside the app, the fd cap, the env-mismatch sweep, a wedged holder, and 200 agents flipping status.
